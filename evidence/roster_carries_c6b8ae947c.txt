-- carry 0: Owner requirement 2026-11-13, his words: "Basically, the objective function should be such that a perfect model that reads it, should be able to improve the dimensions, process and machinery so that that round is completed perfectly against all dimensions, in a perfect way". This is the acceptance test for the definition: it must be sufficient on its own. So the policy file (1) defines the perfect round as an end state, not only directions of improvement: for every dimension what a perfect result is (for objective defects: none remaining in the whole enumerated scope; for dimensions that need judgement, the owner-set acceptance criteria, listed as decisions for the owner where they do not exist yet), and for the process what perfect execution is (every item right first time, no waiting, no rework, no token spent that changes no outcome), each with the measured distance from it; (2) is self-contained: a reader with only the file and the tree can derive what to change in a dimension brief, a role contract or an instrument to close that distance, with no knowledge held in a session, a memory or an earlier round s conversation; (3) says for each term what the residual is that no reader could remove (a floor set by CI wall clock, by the owner s review, by information that does not exist), so perfect is distinguished from impossible. The body states, as its own check, what a perfect reader would change for round 11 from this file alone, and what it could not decide without asking the owner.
-- carry 1: Owner requirement 2026-11-13, his words: "Running that perfect audit round should result in perfect production code". So the function is anchored on the product, not on the process: the terminal objective is the state of the production code after the round, and every process and machinery term is instrumental to it. The policy file therefore (1) defines perfect production code as the conjunction of every dimension s perfect result, and states what makes that set of dimensions complete: a defect or shortfall of the production code that no dimension would call a failure is a hole in the definition, so the function carries a term for the completeness of the dimension set itself (escapes and owner reports that belong to no dimension, counted per round, target none) and the round-start evaluation must propose the dimension or widening that closes each one; (2) shows the chain from a perfect round to perfect code and names each link that must hold: every item in scope examined, every real defect found, every finding fixed correctly, no fix injecting a defect, nothing merged between the examination and the round s close that was not itself examined; for each link, the term that measures it and the residual probability that it fails; (3) says what one perfect round can and cannot guarantee (a single round reaches perfect code only if the links hold with certainty; where a link is probabilistic the claim is convergence over rounds) and never states the stronger claim where only the weaker is supported.
-- carry 2: Owner requirement 2026-11-13, his words: "In the definition of perfect production code should also be that the integration is perfecty generic and can run every install in a perfect way, resulting in perfect savings". So the definition of perfect production code has three product terms beyond freedom from defects, each with its perfect end state, its measure and its irreducible floor: (1) generality: the integration runs correctly on every install in the population it claims to support, with no behaviour that is right only for the owner s own hardware, tariff, climate or configuration; state how the install population is enumerated (pump makes and control interfaces, with and without each optional sensor and actuator, tariff and price shapes, climates, house and tank sizes, duty modes, languages, Home Assistant versions), what examined means for a configuration no seat can run on real hardware (simulation, recorded bundles from D15, contributor installs, property tests over the configuration space), and the distance measure (share of the enumerated configuration space exercised end to end; defects found on an install that the owner s install could not have shown); D12 owns generalization today: say what its brief must change to carry this term; (2) operation: on each install the plan the integration executes is the right one and is executed as planned (every actuator write happens, holds and releases as intended; comfort and safety constraints never violated); tie this to the new actuator-write dimension and to D8; (3) savings: the realised cost against the best achievable for that install under its constraints, so perfect savings is zero regret against an oracle plan given the same prices, weather, house and comfort bounds, and against perfect foresight as the stated upper bound; state the enumerator (D0 owns price optimality: its measure, the flat-price null control every quantified savings claim already owes, the measured-against-modelled gap from live diagnostics) and the floor (forecast error, sensor error, pump limits) that no code can remove. For each of the three, say what is NO-READ today and which record or harness would make it readable, and add the acceptance criteria the owner must set (the supported install population; the comfort bounds savings may never trade against) to the Decisions for the owner section.
