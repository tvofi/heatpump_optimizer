Closes #2023

**1. The carry — `tools/pr/app_approve.sh carry()`.** A commit under one of these subjects may change `main`'s merge-driver files and that subject's own paths, and nothing else:

| subject | own paths |
|---|---|
| `ci: pin killed mutants` | the mutation ledger |
| `ci: re-record closures` | `tests/closures.json` |
| `ci: drop inherited claims` | the claim files |
| remerge_main.sh's `claims: drop the claims main already carries after the main merge` | the claim files |

Two rules for a bot subject: its author must be that subject's writer (`github-actions[bot]` for the `ci:` subjects, the orchestrator's `tvofi` noreply address for remerge_main.sh's), and a claim-file subject may only remove lines. What those commits wrote is left out of the branch's own-diff comparison, so #1667's rule over a seat's commits is unchanged.

**Disclosure.** Author and subject are git metadata anyone who can push may write, so a seat that forges the bot's identity can still carry a `killed_by` entry no run measured. That is the same reach a seat's own ledger edit has, and `policy_lint.mjs` says the same of pr-contract's acceptance. Seats commit as `tvofi`, so the `claims:` author check binds nothing against a seat; its remove-only rule is what stops a forged one from adding a claim.

**2. The merge-main bot — `tools/pr/merge_main_bot.py`, `.github/workflows/merge-main.yml`.** On each push to `main`, a pull request gets a `ci: merge main` commit only when all of these hold: GitHub reports it unmergeable; its head does not already contain that `main`; git's own text merge (every driver replaced by `git merge-file`, which is GitHub's view) conflicts, and only on paths `main`'s `.gitattributes` routes to a driver; and `main`'s real drivers then resolve every one of them with no `refused`. Any other conflicting path is left for a human. It runs `main`'s copies only — `git merge-tree` in a checkout of `main`, then `commit-tree <tree> -p <head> -p <main>` — so nothing from the pull request's tree executes in a job that can push; the first-parent shape is a seat's `git merge origin/main`, so `--carry` judges it as an automatic merge. One push per pull request per push to `main`, never forced; a head that moved since the read is skipped. Its own push lands on a pull-request branch, which no `push: main` trigger sees, and the head it leaves contains `main`, so a second run does nothing. A branch name outside `[A-Za-z0-9._/-]` is skipped, because the pull request chose it. It has a dry run (`workflow_dispatch`, `dry_run` defaults to true) and a `--self-test`, which governance.yml now runs.

**3. pr-contract accepts that one commit shape, and only it.** `AUTOFIX_BOT_COMMITS` gains `ci: merge main`, a two-parent commit, accepted only when its second parent is on `origin/main`, its tree is git's own merge of its parents outside the driver files, and those driver files are read from `origin/main`'s `.gitattributes` rather than the parent's. The walk then continues down the first parent. A clone without `fetch-depth: 0` refuses rather than assumes.
