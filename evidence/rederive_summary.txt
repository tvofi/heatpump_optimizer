## Friction assessment (merge-main bot could ship a false census pair)
NOT true of the merge-main bot as landed. The bot (tools/pr/merge_main_bot.py) pushes a
resolution ONLY when every conflicting path is a `.gitattributes` driver file
(tests/golden/claimed_drift.txt, card_claimed_drift.txt, mutation_budgets.json,
structure_budgets.json, closures.json, bugclasses.json) that its driver resolves.
Census figures live in claims.py / architecture.md / deployment_shape.py — none is
driver-routed, so any conflict on them is `skip-other-conflict` and the bot refuses to
push. A clean false-agreement merge (both sides identically wrong, e.g. architecture.md's
naive merge-tree result = 74) is NOT a conflict, so the bot never fires on it; that hazard
is plain git three-way merge, present with or without the bot, and the bot neither can nor
does union two census numbers. The census IS caught downstream: claims.py's arch counts are
an assertion harness_headers.py executes every PR (REGISTER_DIRS includes D6), and
entities.py pins deployment_shape.py's three headline numbers to the closures derivation —
so a wrong census number in those goes red in CI. The one genuinely uninstrumented figure
is deployment_shape.py's at_1.00 COUNT and per-pair shared-file counts (entities checks only
the 3 headline numbers), which would ship silently if wrong — but that is an instrument-scope
gap in the census lane (D6/deployment_shape note), not a property of R9-CI-2b / the bot.
