# RCA-1869: production imported a Home Assistant name the 2025.2.0 floor does not have (R9-EG-B4)

The root-cause seat for PR **#1869** (R9-EG-B4, #1740). It ran beside the fix, not
inside it (`tools/audit/briefs/root-cause.md`, `.claude/rules/defect-root-cause.md`).
Sections 1 to 4 are that seat's analysis. Section 5 is the countermeasure as the
barrier PR landed it, with the figures that PR measured.

- Defect head: `ef37a5ba1`. The import entered at `4197a3235`.
- Fixed head: `e43ae8dc9`, which guards the import.
- Base: `03ba7f70f`.

**Trigger:** 2 of `defect-root-cause.md`. The defect turned `nightly-ha (2025.2.0)` red: run
37078665491, job 111074155720, `workflow_dispatch` on `fix/r9-eg-store-version`, 98 s,
`ImportError: cannot import name 'UnsupportedStorageVersionError' from
'homeassistant.helpers.storage'`. The fix review then returned `blocked`. A cheaper detector
exists, and it is demonstrated below.

**Class:** P11 (`bugclasses.json`, `"status": "barriered"`). The only floor oracle on the PR
gate was `tests/hastub`, and the stub defines this name. Because P11 carries a barrier, the
rule owes a class barrier for any instance; the cost test below picks its form.

The seat's instruments stayed in its scratch and are not in the tree: the prototype
`floor_names.py` (sha1 `d6de84f7`), `sweep.py` and their outputs. The prototype is
superseded by `tests/ha_floor.py` (section 5). Every seat run used Python 3.14 on macOS. The
upstream source was fetched with `gh api repos/home-assistant/core/contents/<path>?ref=2025.2.0`.

## 1. Root cause

### Cause (reproduced)

`store.py:36` at `ef37a5ba1` reads
`from homeassistant.helpers.storage import Store, UnsupportedStorageVersionError`. The class
is absent from `helpers/storage.py` at 2025.2.0. The fix reviewer measured it as absent at
every tag through 2026.2.3 and present from 2026.3.0. `store.py` is reached by every module
that persists anything, so the integration fails to import on every supported release before
2026.3.

The fixer's census (`census_fixer.py`, run by the seat unchanged) gives:
- `ef37a5ba1`: `pairs=65 missing=1`, `MISSING homeassistant.helpers.storage.UnsupportedStorageVersionError at store.py:36`;
- `e43ae8dc9`: `missing=0 guarded_absent=1`;
- `03ba7f70f`: `missing=0`.

The census exits 0 in all three runs, so it is a census, not a check.

**Which side moved** (`git log -S UnsupportedStorageVersionError`):

1. `3db3eecf2` (R9-F10.1b, 2026-09-30) put the class into the stub and wrote its post-floor
   status down twice:
   - in `tests/ha_contract.py`'s INVENTORY, as a SIMPLIFIED entry: *"the class is in HA
     releases after the 2025.2.0 floor"*;
   - in the `_store_version` contract, marked `expect="stub"`.
2. The same commit added the forward carry `carry-1649.json` `/carries[3]/brief` for R9-EG-B4:
   *"a load of a document saved at a newer version raises UnsupportedStorageVersionError
   before any migration … R9-EG-B4 lands the production seam"*. The carry states upstream
   behaviour from 2026.3 onward as upstream behaviour in general. It drops the floor
   qualifier that the inventory entry, written in the same commit, carries.
3. `4197a3235` (R9-EG-B4) followed the carry and imported the name. The stub defines it, so
   every local check and every PR-gate lane passed.

So production moved, steered by a carry. The stub had moved first, and that move silently
removed the only floor detector the PR gate had for this name: an import of a name the stub
lacks fails at collection.

**Why `tests/entities.py` P6 G did not catch it.**
- `_p6_arm_g` inspects only `ast.Call` nodes whose function is `getattr` or `hasattr` and
  whose second argument is a string constant. An `ImportFrom` is never in its unit.
- Its universe is what production itself defines, plus the hand list `P6_UPSTREAM_PROBES`.
  That list is an allowance; nothing measures it against any Home Assistant version.
- P6 G is P6's barrier (a read with no producer), not a floor check. It cannot see a direct
  import, and it has no idea what exists at 2025.2.0.
- It also cuts the wrong way for this class. The fixer's first repair, `012230171`, was the
  safe `getattr(ha_storage, "UnsupportedStorageVersionError", None)`, and P6 G refused it as
  a test-double-only name. The repair was redone as a guarded import (`e43ae8dc9`, whose
  commit message says so). For P6 G, the unsafe direct import was silent and the safe probe
  was a finding.

**Why the P11 barrier (`tests/ha_contract.py`) did not catch it.**
- Its INVENTORY demands a disposition for every stub symbol and got one. The disposition
  vocabulary is FAITHFUL, DIVERGENT, UNVERIFIED, SIMPLIFIED and HOLDER. None of them means
  "absent at the floor", so the fact lived in prose that nothing reads.
- The file deliberately never opens production (its header, and the #590 note). So no check
  in it can ask whether production reaches a post-floor stub symbol.
- `--compare` compares PROBES only, and only nightly.

## 2. Process state: **(c)**, followed and did not produce the intended result

Three processes bore on this. All three were followed:

1. **The P11 barrier.** `ha_contract.py`'s completeness check required a disposition for the
   new stub symbol, and the author gave one that states the floor fact. The check passed, as
   designed. Its unit is the stub symbol's behaviour and disposition. Production's reach of
   that symbol is outside the unit by construction.
2. **Finding propagation** (`finding-propagation.md`). F10.1b put the constraint into
   EG-B4's carry before it merged, as the rule requires. The carry was obeyed, and it was
   wrong: the floor qualifier was lost between the inventory sentence and the carry sentence
   of the same commit.
3. **The nightly floor arm.** It is deliberately not on PRs (`tests.yml`: *"Nightly and on
   demand, never on a pull request"*). It caught the defect when dispatched, in 98 s.

Not (b). No brief or rule asks a fixer to check a new Home Assistant name against the floor:
`git grep -i 'floor\|2025\.2\|nightly-ha'` over `fixer.md`, `fix-review.md`, `CLAUDE.md`,
`.claude/rules/` and the steward skill finds nothing on point. "Tell the fixer harder" would
be the (b)-shaped countermeasure, and it is refused here.

Not (d). The precondition the stub-as-floor-oracle relied on (stub ⊆ floor) was not changed
underneath the process. It was changed by a seat following the inventory process, which
recorded the change and attached no consequence to it. The countermeasure therefore changes
the unit: from "stub symbol" to "every Home Assistant name production reaches, against
upstream at the floor". It does not add an arm to the inventory.

rounds, so **about 0.19 per round**. This is a lower bound; see the class search.

**cost(defect), per occurrence:**

### Secondary: the carry that dropped the qualifier

The carry text was the proximate steer. A per-carry rule ("state the version range of
every upstream behaviour you carry") is a (b)-shaped instruction for a (c) state, and the
check makes the carry's omission harmless. **No countermeasure is recorded for the carry**,

## 4. Countermeasure, as the seat specified it

The barrier is a check, not an instruction. It reads its population off production, never
off a list.

**Unit.** Every Home Assistant name production reaches unguarded, in three arms:
- **I:** `from homeassistant.M import N`. N must be bound at module scope of M at the floor,
  or M.N must be a module.
- **A:** `alias.N` where `alias` is a Home Assistant module, e.g. `ir.async_create_issue`.
- **C:** `Cls.N` where `Cls` is a class imported from Home Assistant whose chain is decidable
  in its module. Arm C reaches the v6.3.1 shape.

**Guards.**
- Guarded means inside a `try` whose handlers catch `ImportError`, `ModuleNotFoundError` or
  `AttributeError`, or under `if TYPE_CHECKING:`.
- Annotation subtrees are typing-only and excluded. All 69 production modules carry
  `from __future__ import annotations`, so no annotation is evaluated at run time.
- Without that exclusion, the one false positive at main was `config_flow.py:1041`'s local
  annotation `selector.EntityWithDeviceFilterSelectorConfig`. That name is post-floor but
  never evaluated.

**Fail-closed.** A module production imports that the snapshot lacks is a FAIL
(`UNRECORDED`), so a new import cannot go green by being unknown.

**Snapshot.** Recorded from upstream source at the floor by the tool's `record` mode and
never written by hand. The nightly floor container verifies it, so a hand edit reddens
within a night.

**Node ids per file.** A first draft of the prototype held the typing-only node ids in a
module-global set across files. Recycled `id()`s then turned `ef37a5ba1` green. Per-file sets
fixed it, and a port must keep the node ids per tree.

**Residual, stated:**
- An inherited class member from outside its module is undecidable. The count is 0 in every
  tree today, and it is printed rather than failed.
- A `try` guarded by `except Exception` is flagged, which is the fail-safe direction.
- Behaviour that changed under an unchanged name is not covered. That is `UPSTREAM_DRIFT`'s
  ground, and stays nightly.
- The stable arm's names are not checked. Only the floor is a supported-version contract.

**Should P6 G change?** Not owed. Under this barrier, both P6 G and the floor check accept a
guarded import, and that is the form `e43ae8dc9` landed.

## 5. Countermeasure as landed

- **The check:** the section "P11: every Home Assistant name production reaches exists at
  the floor" in `tests/entities.py`. Its unit, guards and fail-closed rule are section 4's.
  It reuses P6's parsed trees and walks (`_P6_TREES`, `_P6_WALKS`); its recorded closure
  already holds every production `.py`. `tests/ha_contract.py` cannot host it: it must not
  open production.
- **The library and tool:** `tests/ha_floor.py` (`NOT_A_TEST` in `tests/closure.py`). The
  arms read it; its `record` mode answers each question the check asks, by walking the
  check's own decision path against upstream source at the tag, so it records nothing the
  check never reads.
- **The snapshot:** `tests/ha_floor_names.json`, one recorded answer per question:
  `module:`, `name:` and `member:` keys. A question it does not hold is `UNRECORDED`, a
  name as well as a module.
- **The truth control:** a step of the `nightly-ha` job on the `2025.2.0` arm,
  `python tests/ha_floor.py verify`, which re-asks every recorded answer of Home Assistant
  itself in the floor image and fails on any disagreement, on a version that is not the
  snapshot's tag, or on zero questions asked.
- **Its wiring pin:** a check beside the `nightly-ha` install pin in `tests/entities.py`.

Two departures from the seat's specification, each a tightening:

- **Arm C follows re-exports.** `HVACMode`, `SensorDeviceClass` and their siblings are
  defined in a component's `const.py` and re-exported by its `__init__.py`; the record follows
  `from .const import X` to the defining module. Without that, every member of those classes
  would have been undecidable, which is where a v6.3.1-shaped defect would hide.
- **Fail-closed covers names, not only modules.** The snapshot holds answers, not a module's
  whole namespace, so a new name in an already-recorded module is `UNRECORDED` too, and
  re-recording shows each new name in the diff.

The figures, their commands and their controls are in the barrier PR's body.

**Where the record correction went.** `carry-1649.json` `/carries[3]/brief`, the EG-B4
carry, gains "(2026.3+)" after the name.
