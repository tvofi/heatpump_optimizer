# D13 — Process yield and cost

Owner's brief: *"a governance structure that enforces this and has good first
pass yield."*

Read `COMMON.md` first. D11 audits the mechanism: does a refusal fire when it
should. You audit the outcome: what the process pays per merge, and how often
a pull request passes first time. A check that does not fire is D11's finding;
a check that fires correctly while the process still pays N rounds for it is
yours. You read the same sources D11 does — `main`'s history, check runs,
comments, reviews, bodies — from a worktree with `.git`, each recorded under
`exposure`; the verdicts' content is your population, never your evidence.

## Required outputs

Each with its rule beside it and its enumerator named; every count derived at
your own window, none carried from a document or a comment.

1. **First-pass yield and rounds per merge.** Population: merged pull
   requests whose merge commit is first-parent in the window, from
   `/commits/<sha>/pulls` — the API mode of `policy_lint.mjs`'s
   `enumerateMerges` — with `api_failures` printed beside the count. A
   verdict is an issue comment *or* a pull-request review whose first line
   matches `^Fix review:\s*(merge|blocked)`, ordered by time. Yield is the
   share whose first verdict is `merge`; rounds are verdicts per merge, mean
   and max.
2. **Verdict coverage by class.** Merges with no parsable verdict, split by
   title prefix and author: fix and feature, record and chore, bot cycles,
   other lanes. A class is exempt only by a rule you can cite beside the
   row; no rule in the tree exempts record pull requests today.
3. **Block classes, three ways.** Every `blocked` verdict by the class in
   `web-fix-wave.js`'s `VERDICT_CLASSES`, then bucketed engineering /
   record-and-body / orchestration; the bucketing is yours, stated in the
   harness header. A class the grammar does not have is its own row.
4. **DORA's four keys, by job.** `tools/audit/round4/D11/dora_keys.py` is the
   base; its failure rate is per *workflow*. Re-take it per check-run name
   from `d11lib.py`'s `check_runs`, then again against a by-design-red
   exclusion list — a small JSON file beside `policy_budgets.json`, read by
   nothing yet. Creating that list, with a reason per job, is part of your
   first round, not a precondition for it.
5. **CI seconds per merge, governance against the gate.**
   `governance_cost.py` and its `GOV` set, re-derived from the workflow files
   at your window: jobs have been added since it was recorded.
6. **The friction histogram's labelled fraction.** `policy_lint.mjs --stats`
   keys a `## Friction` bullet on its first backticked span and reads bodies
   only; the template's line form has no backticks. Report the fraction
   labelled and, separately, the fraction whose key is a rule file.

## Perturbation

A yield figure must move under a named change, in a fixture and never on a
live pull request: one verdict comment re-shaped out of the grammar lowers
coverage by one; one job added to the exclusion list moves the failure rate by
exactly that job's count; one friction bullet's backticks removed moves the
labelled fraction by one. A harness whose number does not move is void.

## Severity

`high` — a measured cost exceeds what the mechanism it pays for catches, e.g.
more review rounds spent on body figures than on any engineering defect over
the window; `medium` — an instrument that cannot compute its own metric;
`low` — hygiene.

## What has fooled people before

- The grammar is `web-fix-wave.js`'s `VERDICT_RE`. A hand-written verdict can
  fall outside it (`Fix review: PASS — merge <sha>` did); `--stats` prints it
  as outside the grammar. Count it on its own row, never fold it in silently.
- `policy_lint.mjs`'s `fetchWindow` reads issue comments only. A verdict posted
  as a pull-request review is invisible to it and to that endpoint; read
  `pulls/<n>/reviews` too and say which endpoint each verdict came from.
- `--paginate` on an object endpoint concatenates page objects; decode each
  and join their `check_runs`, as `d11lib.py` does.
- A count of merges compares the set of numbers against the API, never totals.
- A matrix job's check-run name carries its leg (`fast (3.14)`); keying on the
  bare job name counts zero. A skipped run's duration is negative; sum only
  runs that concluded.
- `actions/runs` caps at 1000 results and silently truncates a longer window;
  per-commit check runs have no such cap.
