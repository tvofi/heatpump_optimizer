# D4 — UI/UX

Owner's brief: *"UI/UX — the card and the config flow, including grouping and
setup ergonomics. It should be intuitive, user friendly and look professional."*

Read `COMMON.md` first.

## Method

1. **The card in a real browser.** Install Playwright into a scratch prefix
   (`npm i --prefix <tmp> playwright@1.49.0`, `NODE_PATH=<tmp>/node_modules`,
   `PLAYWRIGHT_BROWSERS_PATH=~/.cache/pw-browsers`, Chromium is already
   there). Build the card the way `tests/card_browser.mjs` does, drive every
   state in `tests/card_drift.mjs`'s `STATES` (`--list`), at viewports
   375×812, 768×1024 and 1280×800, light and dark, `sv` and `en`,
   reduced-motion and coarse pointer. Measure with `getBoundingClientRect`
   and `getComputedStyle`: overlapping text boxes, text that overflows its
   box, WCAG AA contrast of every text/background pair, hit targets below
   24 px (44 px on the coarse pointer), keyboard tab order through every
   focusable, console errors, layout shift on hover. Screenshots go in your
   report directory. **The coarse arm is coarse for JavaScript, not for
   CSS.** No emulation in this Chromium drives the `pointer` media feature:
   CDP `Emulation.setEmulatedMedia({features:[{name:"pointer",value:"coarse"}]})`
   leaves both `matchMedia("(pointer: coarse)").matches` false and an
   `@media (pointer: coarse)` block unmatched. Control: a minimal page whose
   `#t` is 24 px with a coarse-only 44 px override reads 24 px in the coarse
   arm; the card's own `.chip` reads 24 px under the same coarse page, and
   44 px only once the card keys its floor on its `_coarsePointer()` read. So
   the arm is coarse because `tests/card_browser.mjs` installs an in-page
   `window.matchMedia` stub, which is the card's own predicate — a card fix
   written INSIDE `@media (pointer: coarse)` measures as no change here and
   cannot be priced. The card has one coarse predicate, `_coarsePointer()`,
   the same one `_targetMinPx()` uses (R5-D4-03, #1320).
2. **The config flow.** Drive every page through the stub the way
   `tests/entities.py`'s options loops do: field order and grouping, defaults,
   selector ranges, validation error keys and their translations, help text.
   Score each page against a written rubric (one theme per page, related
   fields adjacent, sensible defaults, errors that say what to change, no
   jargon without help text, field count). Count the steps from install to
   the first plan and what a first-time user must know at each.
3. **Professional look.** Consistency of typography, spacing and colour
   tokens across card states; legend and series colours across light/dark;
   alignment of headline numbers; empty and error states.

## Numbers

Pixels of overlap, contrast ratios, hit sizes, counts of fields and steps —
all contention-immune. A finding says which state, which viewport, which
element, and what a user cannot do or read because of it.
