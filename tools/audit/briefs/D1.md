# D1 — Robustness and stability

Owner's brief: *"Robustness and stability — lifecycle, staleness, executor
boundaries, store corruption, guards."*

Read `COMMON.md` first.

## What you are hunting

Ways the integration wedges, leaks, races, publishes stale data as fresh, or
turns a corrupt input into a permanent failure — under real Home Assistant
semantics, not the test stub's.

## Method

1. **A real-loop harness.** Subclass `tests/harness.py:FakeHass` so
   `async_add_executor_job` runs in a `ThreadPoolExecutor` on a real
   `asyncio` loop, and `async_create_task` schedules instead of closing.
   Then: setup → first refresh → reload during an in-flight solve → unload
   during an in-flight solve → setup again. Assert no live tasks, listeners,
   timers or executor futures reference the torn-down coordinator
   (`asyncio.all_tasks`, tracked listeners, `gc.get_referrers` on the old
   instance), no exception escapes, and the new instance's first cycle
   completes.
2. **Store corruption fuzzing.** Enumerate every persisted payload
   (`Store(`, `async_load`, `_async_save`, snapshots, ledger, learners,
   manual plan). For each, generate mutants from the healthy payload with a
   seeded RNG: field type swaps, missing keys, `NaN`/`inf`, negative and
   huge numbers, wrong nesting, truncated lists, strings where dicts go —
   at least 200 per store. Load through the real loader, run one cycle,
   assert the cycle completes, the corrupt part is quarantined or reset with
   one log line, and the *next* cycle does not repeat the failure.
3. **Staleness.** Drive the watchdog and every "age" sensor under: a frozen
   clock jump forward/back, DST transitions (`tests/hastub` `dt.freeze`,
   `tests/dst_checks.py`), `last_reported` in the future, states `unknown`
   and `unavailable`, a price list that stops updating, a weather entity
   that returns an empty forecast. The published values must say stale when
   stale and never present fabricated data as measured.
4. **Executor boundary.** From `_solve_snapshot` and the executor lambda,
   list every `self._*` the solve thread reads; from the loop side, every
   writer of those attributes. A runtime race harness mutates each writer
   mid-solve and checks the plan and the published payload for torn state.
5. **Guards.** Every `try/except` that swallows: does it log once, does it
   set `last_update_success`, does it recover on the next cycle, does it
   hide a bug that should surface? Executed by injecting the exception.

## Reuse

`tests/harness.py`, `tests/entities.py:_honest_coordinator`,
`tests/golden.py:_capture_coordinator`, `tests/hastub/homeassistant/util/dt.py:freeze`.

## Traps

`FakeHass` serialises the executor and closes coroutines — a race that only
reproduces by calling `async_shutdown()` directly, bypassing the config-entry
state machine, is a stub artefact. Real HA serialises setup and unload per
entry; state your claim against that.
