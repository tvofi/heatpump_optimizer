# D1 — Robustness and stability

Owner's brief: *"Robustness and stability — lifecycle, staleness, executor
boundaries, store corruption, guards."*

Read `COMMON.md` first.

## What you are hunting

Ways the integration wedges, leaks, races, publishes stale data as fresh, or
turns a corrupt input into a permanent failure — under real Home Assistant
semantics, not the test stub's.

## Method

1. **A real-loop harness.** Subclass `tests/harness.py:FakeHass` so
   `async_add_executor_job` runs in a `ThreadPoolExecutor` on a real
   `asyncio` loop, and `async_create_task` schedules instead of closing.
   Then setup → first refresh → reload mid-solve → unload mid-solve → setup
   again. Assert no live task, listener, timer or executor future references
   the torn-down coordinator (`asyncio.all_tasks`, `gc.get_referrers`), no
   exception escapes, and the new instance's first cycle completes.
2. **Store corruption fuzzing.** Enumerate every persisted payload
   (`Store(`, `async_load`, `async_save`, snapshots, ledger, learners,
   manual plan). Per store, at least 200 seeded mutants of the healthy
   payload: type swaps, missing keys, `NaN`/`inf`, extreme numbers, wrong
   nesting, truncation, strings where dicts go. Load through the real loader,
   run one cycle, assert it completes, the corrupt part is quarantined or
   reset with one log line, and the *next* cycle does not repeat the failure.
3. **Staleness.** Drive the watchdog and every "age" sensor under: a frozen
   clock jump forward/back, DST transitions (`tests/hastub` `dt.freeze`,
   `tests/dst_checks.py`), `last_reported` in the future, states `unknown`
   and `unavailable`, a price list that stops updating, a weather entity
   that returns an empty forecast.
4. **Executor boundary.** From `_solve_snapshot` and the executor lambda,
   list every `self._*` the solve thread reads and every loop-side writer of
   them; a race harness mutates each writer mid-solve and checks the plan and
   the published payload for torn state.
5. **Guards.** Every `try/except` that swallows: does it log once, does it
   set `last_update_success`, does it recover on the next cycle, does it
   hide a bug that should surface? Executed by injecting the exception.
6. **External-input parsers.** Every parse of input the integration did not
   produce — ECL110 MQTT, pump-signal states, the Tibber and Open-Meteo
   responses, the weather forecast — driven with malformed, non-finite,
   oversized and hostile payloads: the cycle completes, the failure logs once,
   the arm is pinned. `coordinator.py`'s MQTT handler ends `except Exception:
   return` under *Ignore malformed payloads*: no log, and `NaN` is stored.

## Reuse

`tests/harness.py`, `tests/entities.py:_honest_coordinator`,
`tests/golden.py:_capture_coordinator`, `tests/hastub/homeassistant/util/dt.py:freeze`.

## Traps

`FakeHass` serialises the executor and closes coroutines. Real HA runs setup
and unload through the config-entry state machine, one at a time per entry; a
race reproduced only by calling a lifecycle method directly is a stub artefact.
