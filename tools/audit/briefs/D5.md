# D5 — Docs structure, flow and content; code comments

Owner's brief: *"Docs structure, flow and content. Verify claims in docs.
Comments in code should be concise but precise and easy to understand."*

Read `COMMON.md` first. D6 verifies README and documentation claims
one by one; you own structure, flow, content quality and the comments in
code. Coordinate by scope, not by talking: claims you meet on the way go in
your report tagged `for D6`.

## Method

1. **Reader paths.** Walk three readers through the docs: a new user
   installing via HACS to a first plan; a user configuring a specific
   feature (two-tank storage, ECL110, capacity tariff); a developer running
   the tests. Record every dead end, forward reference, contradiction and
   place the reader needs a fact that is elsewhere or nowhere.
2. **Structure.** Heading depth and order, duplication between README and
   `docs/*.md` (measure with paragraph hashing), orphaned documents, link
   check on every internal and external link, stale version numbers.
3. **Content.** Every paragraph that explains a mechanism: is it true to
   the code (spot-check by reading the code path), current (grep for the
   symbols it names), and needed?
4. **Comments in code.** Sample every module's docstring and every comment
   over three lines. Executable check: identifiers a comment names must
   exist (grep), numbers a comment cites must match the constant beside it.
   Judge concision and precision; list comments that explain *what* the
   next line obviously does, and comments that are wrong.

## Numbers

Dead-end count per reader path, broken links, duplicated paragraphs,
comment-named symbols that do not exist, cited numbers that disagree with
code.

## Exposure

You must read `docs/`, which includes `docs/audit-2026-08.md` and in-code
comments citing earlier finding ids. Record that in `exposure`; do not use
them as a list of things to re-find.
