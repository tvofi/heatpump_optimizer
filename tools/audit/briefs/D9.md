# D9 — CPU and memory efficiency (Raspberry-Pi-class target)

Owner's brief: *"CPU and memory resource efficiency — target hardware is
Raspberry-Pi-class running all of Home Assistant. Measure, don't assert:
express findings as relative cost (share of a solve, allocations per step,
bytes retained, renders per gesture), include the harness, and state the
extrapolation wherever a Pi conclusion is drawn. A finding without a
measurement is not a finding. Priorities: the finite-difference gradient
(~9,300 simulate_step calls per L-BFGS iteration); the longest contiguous
GIL-holding interval (v5.1.1 added just two 2 ms yields in a multi-second
solve, and a cold solve once made the whole HA instance unreachable); how
many full solves a cycle actually runs; the DHW planning loops; per-cycle
loop work outside the executor; retained collections with no trim; published
payload size versus the recorder exclusion set; and whether the stress budget
should become a real gate — CI sets it 4× looser than the default, so it
cannot detect anything short of a 4× regression, and there is currently no
memory instrumentation anywhere."*

Read `COMMON.md` first. You have an isolated worktree for instrumentation.

## Metric definitions (fixed, so two agents cannot score different things)

- **Simulate-step-equivalents per gradient** = scalar `simulate_step` calls
  + rows of `simulate_trajectory_batch`, both hooked by monkeypatching the
  production symbols, per gradient evaluation of `_multi_start_minimize`.
  Report for: the default two-zone DHW solve, the single-zone solve, the
  zero-range-bounds fallback (a manual pin; a DHW block consuming the whole
  cap), and each DHW planning loop.
- **Full solves per cycle** = entries into `_multi_start_minimize` during
  one coordinator cycle, split by path (main solve, shadow/what-if,
  diagnose, any other).
- **Longest contiguous GIL hold** = the maximum gap between 1 ms heartbeat
  ticks of a task on a real event loop while the solve runs in a
  `ThreadPoolExecutor`; **starvation share** = the fraction of the solve's
  wall time during which the gap exceeded 5 ms. Never on `FakeHass`.
- **Loop-thread work per cycle** = `time.thread_time()` on the loop thread
  across one cycle, excluding the executor.
- **Retained bytes** = `tracemalloc` and deep `sys.getsizeof` of every
  coordinator collection after N cycles, as a slope per cycle, plus
  `ru_maxrss` in a subprocess.
- **Payload bytes** = JSON bytes of `_build_data_dict` and of every entity's
  attributes, split by what `_unrecorded_attributes` excludes, per cycle
  and per day.

## Method

One harness file per metric under `tools/audit/round2/D9/`, each with the
header the contract requires, each hooking a named symbol and moving under
a named perturbation (e.g. `maxiter`, horizon length, cycle count). Use
`tests/stress.py:reference_solve` as the ruler for every "share of a solve".
Then: does the stress gate as shipped in this tree detect a synthetic 2×
regression (inject work into the solve and run its checks)? What does it
cover, what can it not see?

## Extrapolation

Every Pi statement carries the factor and its source (state it as an
assumption if it is one) and the M1 number it scales from.

## Traps

Timing during the fan-out is provisional; counts, bytes and CPU ratios are
final. Pin threads before numpy; print `thread_factor`. The two existing
`sleep(0.002)` yields sit between L-BFGS starts and between the DHW and
space stages, not inside an iteration.
