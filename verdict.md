## Cloud seats for speculative gating, on haiku (the owner's variant)

**What it can replace safely.** The search, never the proof. (1) Bisection of a red batch: one seat a prefix, all at once, names the first red prefix in one seat wall instead of two to four serial proof walls; the green prefix still needs its one authoritative proof on GitHub before main moves. (2) A pre-proof that picks the next batch: while the proof of one tip runs on GitHub, seats run the next tip and a predicted-red landing is held out of the next proof. (3) A gate on SUCCESSORS: a successor starts when a seat has run the gate green at its predecessor's landing, a third state between landed and promoted. That answers R4's risk, and it adds the seat wall, about 1.1 h, to the landing figure: 2.50 + 1.1 = 3.6 h, which is C1's 3.45 to 3.67 h to main. The variant makes the integration branch safer and removes its wall-clock edge over day 1 at the same stroke.

**What it cannot replace.** Anything that must be a GitHub check: the `gate` at the reviewed head that landing reads, and the proof at the tip. CodeQL, the environment matrix and the jobs that call the GitHub API do not run in a seat. Value-bearing golden fixtures: `cloud-setup.sh` pins `OPENBLAS_CORETYPE=Haswell` (line 57) and hash-pinned wheels, and `--check` refuses without them, but no workflow except kernel-points.yml sets that variable, so a seat's floats are not shown equal to the runner's; a golden red or green from a seat is inconclusive until measured. Closure recording under `strace` is unverified in the seat's container.

**Trust.** A seat's result is a ref, not a check. It may reorder, hold out or name a suspect; it may never promote, evict or post a verdict. An absent ref after the deadline is no result, never green.

**Is the haiku constraint achievable as stated? Yes, if the judgement is in a script and not in the prompt, and that script does not exist yet.** The design owes one tracked instrument with a self-test, say `spec_gate.sh <tip-sha> <base-sha> <full|scoped>`, that does everything: runs `cloud-setup.sh --check` and on refusal writes `REFUSED env` as the result; fetches the tip and refuses unless the fetched sha equals its argument; checks it out detached; runs the one fixed invocation (`GATE_SCOPE=full ./tests/run.sh`, or `GATE_SCOPE=auto GOLDEN_MODE=drift GOLDEN_REF=<base-sha> ./tests/run.sh`); takes the exit code and the failing script names from `run.sh`'s own summary; reports scripts on a fixed list (the golden and closure-recording ones) as INCONCLUSIVE itself; appends the result to `spec/<tip-sha>`; prints one `RESULT` line. Today "the gate scripts" is not one command: the instrument self-tests and policy lanes are jobs in governance.yml, so the note must say which of them the seat runs. **The seat's prompt then holds only:** the repository source (a fire without sources ends in 20 s reading succeeded); that one command with the literal shas; "run it, wait until it exits, reply with its last line verbatim"; "if it prints REFUSE or has not exited after N minutes, reply with that and stop"; and four prohibitions: no other command, no edit, no re-run, no reading of a red.

**Cost a run.** About 60 to 70 seat-minutes for a FULL tip: the suite's CI job `fast (3.14)` has a median of 55.2 min (IQR 41.2 to 56.7, `tools/plan/durations.json`), plus checkout and the environment check; a scoped tip in proportion to its closures. This is an estimate from the CI job, not measured on a seat. A FULL proof on GitHub is 197 runner-minutes across 39 jobs. Bisecting a red range of 12: eleven seats, about 715 seat-minutes in one wall, against four serial proofs, 788 runner-minutes in four walls.

**Does it change the bar's arithmetic? No for the means.** Landing time and so the programme figure do not move; bisection proofs are 2 to 25 of 101 to 149 proofs in the designer's replay, under two points of CI. It changes the tails: culprit known after about one seat wall instead of 2.4 to 10.5 h, and R5's 28.9 h worst lag.

**What must be measured (R11), on the shadow day:** the agreement between a seat's result and GitHub's `gate` at the same sha, false green and false red, by failing script; the seat wall for a FULL and a scoped tip; and the fire-to-result failure rate. Carry: R11-PRE-PARALLEL-PIPELINE (item c1)
