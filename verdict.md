## Revise points (defects in the design)

1. class-open. R10-LIVESTATE.md:74, sibling-sites item 3. The note dismisses 15 of the 17 store-load awaits as "held stores with D1-s2-52's save gate". That reason does not hold for coordinator.py:8239 `_async_load_manual_plan`. It awaits `_manual_plan_store.async_load()`, then writes `self._manual_override = override` unconditionally (coordinator.py:8258). `async_clear_manual_plan` (coordinator.py:8386) and `async_apply_manual_plan` (coordinator.py:8361) write the same attribute before any await and never wait for the read. The save gate protects the disk, not the in-memory attribute: a clear made during the startup load is reverted in memory while the store holds `{}`. This is L3's N-restore-race shape. Probe `evidence/probe_manual_restore.py` (stub store gated on an asyncio.Event; real `_async_load_manual_plan` and `async_clear_manual_plan`): `RESULT lost_midload=1 lost_null=0`. The null is the serial order: clear after the load. Fix wanted: re-disposition the 15 by the class's own criterion: can a writer of the same in-memory attribute run inside the load await? For `_async_load_manual_plan`, either cover it in this shape (the restore gate, or the identity-or-written check, extends to it) or route it as a sibling seam by finding-propagation.md (a new issue filed by the same PR, or a carry file), not "dismissed". notifier.py:268 (`_sent`, written by `handle` each cycle) and debugger.py:476 (rows) have cycle writers of the same attributes: disposition them on the same criterion.
