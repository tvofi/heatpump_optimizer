No such step exists in setup. `_async_load_ledger` (def `coordinator.py:8304`) runs only through `self._spawn(load())` in `__init__` (`coordinator.py:3585`). The method also returns early when no store exists (`coordinator.py:8307-8308`, a fresh install). An attach placed "after the restore" in setup therefore either races the load, which is the very loss test 5 is meant to pin, or sits at the end of `_async_load_ledger`, where it never runs on a fresh install. It can also run after an unload that came first, and nothing would detach that listener. Fix wanted: name the real anchor. That means the load task's completion on every path, the early return included, guarded by `entry_released` against a load that finishes after shutdown, with shutdown (`coordinator.py:6622`) detaching a listener attached late. Test 5 must then pin the fresh-install path and load-after-unload. As written, test 5's "an edge before the restore is not lost" contradicts attach-after-restore.

2. class-open, design.md section 2 "Residual". The note says the latch lag "is the latch's own rule, today and after". The tree does not support that for the counter. `_detect_immersion` runs in `_update_current_state` (`coordinator.py:6711`, called at `:6069`), before `_record_accuracy` (`:6123`) in the same refresh. On the second, the latch is already set (`:9116`), and `StartCounter.observe` freezes and resets the streak (`wear.py:131-133`). So today that window counts no start. On the event path, the meter crosses the threshold, the edge confirms at `EDGE_DEBOUNCE_S` = 30 s (`wear.py:40`), and a start is counted and priced as a wear line one to two refreshes before the latch can mask it. That is a new class of false start in the counter that no finding names. Fix wanted: state it and close it, for example with an element-on read the event path can use inside the lag. Otherwise route accepting it as `decision: owner`, and add the case to test 4 with a mutant.
