## Revise points

1. class-open. accuracy.py:977 (judge_ratio, `abs(ratio - 1.0) <= COP_ASK_TOLERANCE` arm) and the note's Shape "Admission": only departures beyond COP_ASK_TOLERANCE enter the probe. A self-setting pump whose fixed draw sits within the tolerance of the flat ask (for example 1.6 kW drawn on a 1.5 kW ask, ratio 1.067) folds every interval through that arm. The fold's target is `cop_scale * commanded_kw / electrical_kw` (flow_meter.py:122), and its draw never answers the scale, so each fold multiplies the scale by (1 - COP_LEARNING_ALPHA * 0.0625) and walks it to COP_SCALE_MIN. That is the same mechanism the note's "The defect, measured" names. No row of this pump enters the probe, so no verdict latches and invariant (n) never applies. The Sibling sites section excludes only the spanning-ask case (selfmod_independent), not this flat-ask one. Fix wanted: admit unobtainable, with-window intervals inside the tolerance into the probe too (they keep folding while pending, as they do today), or state why not. Add a harness row to cop_duty_floor.py at both ends: a self-setting flat-ask pump with its draw inside the tolerance, on 4 kW, over 672 intervals. The heat-led null control (true 0.8 / 0.68 flat-ask rows and the full-output diff) is re-measured under the widened admission.

2. class-open, the population the released defect already reached. In the Shape "origin" is "the scale the first probed row was read at", and `cop_scale` persists (coordinator.py:4637 load, :4705 save). An upgraded install that the released residual has already walked to COP_SCALE_MIN takes 0.500 as its origin. The scale is clipped there (coordinator.py:5082), so the heat ask `asked_kw * cop_scale` cannot span FOLLOW_ASK_SPAN under flat asks. The probe stays pending forever and the install stays at 0.500, which is D4's symptom, at the fix head. A partly walked install (say 0.6) restores to its own walked value, then the latch refuses every later interval, which freezes the wrong scale. The note says nothing about either case. Fix wanted: state the upgraded install's behaviour, and measure it with harness rows that start from a persisted scale of 0.500 and of 0.7 under the self-setting flat-ask run. Then define the origin so that the restore reaches a scale this learner did not write; on these installs this fold is the only writer, so the configured `_config.cop_scale` (coordinator.py:3857) is one candidate. The clamp case also needs either a remedy or a stated residual. Choosing among remedies that trade off product behaviour (for example a one-off reset of a scale at the clamp on a no-heat, unobtainable install): decision: owner.
