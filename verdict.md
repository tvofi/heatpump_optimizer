## Revise points

1. architecture-unsound, phase 1 read path. inputs.py:1094 `read` parses `float(state.state)` (inputs.py:1108-1112); a `climate`'s state is its HVAC mode, so the read the note builds on returns `not_numeric` for every room thermostat. No reader in the tree returns `current_temperature` or `hvac_action`. Fix wanted: specify the new attribute read on `InputReader` (signature, the unit conversion for each of the three values, what it returns for a `sensor`).
2. architecture-unsound, phase 1 health. inputs.py:153-155 `InputHealth.record` stores `self.readings[reading.key]`; up to 32 rooms under one list key overwrite each other, so "every room read lands in `InputHealth`" is false as designed. Fix wanted: name the health keying (per-room key, or a separate room record outside `InputHealth`), and with it where the age limit and the range register: the range is `INPUT_PLAUSIBLE_RANGE_C` (const.py:1887, read by `plausible_c`, inputs.py:254), not `INPUT_MAX_AGE_MINUTES` as the note says. State what one unavailable thermostat among twenty does to the Input problem sensor (binary_sensor.py:100) and the stale-input event (notifier.py `_inputs`): as written an opted-in install with one dead room shows a standing problem, a risk to existing installs the brief asks the note to state.
3. product-tradeoff-regression, the HVAC-mode rule. The note cites inputs.py:455-505 for "target only while its HVAC mode heats". That range states only that a climate's target is the `temperature` attribute in the instance's unit system; `hvac` appears nowhere in inputs.py. The rule is new behaviour, not an inherited one. Fix wanted: state it as new, with its own failing test and mutation target (a room in `off` or `cool` with a target above its temperature gives no lift).
4. class-open, the lift's gates. The note gates on away only. `_floor_widening` (coordinator.py:6260-6268) lowers the solve floor for Economy (`ECONOMY_MIN_TEMP_WIDENING`) and for a detected open window (`OPEN_WINDOW_RELAX_C`) through the same `solve_bands` path (away.py:399-400); the margin is added after both (optimizer.py:4563). A room with an open window is the coldest room, so the lift rises exactly when the relax lowers the floor and cancels it. Away recovery is also ungated (`floor_drop_c`, away.py:365, is None while recovering). The night setback (optimizer.py:2599-2606) is lifted by the same held amount. Fix wanted: enumerate every floor-lowering site by command, gate or justify each, name which signal "away active" reads, and add a null control per gate.
5. product-tradeoff-regression, behaviours the lifted floor moves that the note does not name. "Sibling sites" covers the coordinator's checks only; inside optimizer.py the lifted `temp_min_bounds` also feeds: `_safety_release_steps` (optimizer.py:5036-5045), which releases a user's manual forced-off pin and raises the manual-plan-released notification; `_derive_hold_schedule` (optimizer.py:4898-4899, `targets[hold] = floors[hold]`), which under smart-write becomes an actuated valve target, against invariant (ii)'s "only raises the floor"; `power_cap_breach_c` (optimizer.py:4678-4684), which feeds the fuse advisor's shortfall and `feasible`; `classify_space_steps` (optimizer.py:2090), narrated as "holding the minimum temperature" (narrative.py:46); and `comfort_band` (optimizer.py:5137), which narrows as the floor rises and so stiffens the pull to target. Fix wanted: list each with "moves, because" or "must not move, and how", and correct invariant (ii).
6. architecture-unsound, floor above target. Nothing clamps the lifted floor to the comfort target: the only clamp is `temp_max_bounds - 0.5` (optimizer.py:4576-4578). The note's own failing-test fixture (live target 20.0, lift at a 1.0 K cap) puts the floor above the target on any install whose band is narrower than the cap, where the floor penalty and the target pull oppose each other and `comfort_band` sits at its 1.0 minimum. Fix wanted: define the behaviour (clip the lift to the band, or state why floor above target is intended) and pin it with a test.
7. harness, the cost and energy evidence misses the case the finding is. The table starts at 20.0 with floor 19.5, so the room never starts below the lifted floor. The reporter's case is a house at 19.6 with rooms under target: the floor is a soft penalty with no ramp for an initial violation (optimizer.py:3246-3310, `_COMFORT_FLOOR_L1` at :1125), so the first solve after opt-in runs at the power bound. The two-zone solve applies one lift to both zones' floors (optimizer.py:3268-3270) though the readings describe one sensed zone. Fix wanted: add a row starting below the lifted floor, single- and two-zone, and a statement of which zone the lift belongs to. Also state the cycle-to-cycle behaviour: the lift is recomputed each solve from one room's reading with no hold, and there is no plan-level hysteresis in the tree.
8. architecture-unsound, phase 3b's channel. `power_caps_extra` is a total-draw cap, not a space-delivery limit: space headroom subtracts the hot-water plan from it (optimizer.py:4743-4750) and the hot-water planner takes its minimum over the whole horizon as run power (optimizer.py:329-333). A "short window" loop cap therefore throttles hot water for the full horizon, and any non-None cap switches on the breach publish and fuse-advisor path. The composition site is also not where the note puts it: the `np.minimum` sits in `_solve_record` before `quiet_windows.compose_with_silent` (coordinator.py:6291-6298), the builds only pass `quiet.caps`, and the what-if build composes no capacity cap at all (coordinator.py:11300-11307), so a cap on the live path alone is differenced against a what-if without it. The envelope the note mirrors is keyed by outdoor bucket and gated by `capacity_curve_enabled`; a calling-share envelope is new stored state whose owning module and store the note does not name, folded "where `_fold_capacity_envelope` folds", which is coordinator code computing at zero headroom on `class_excess_loc` and `max_class_loc`. Fix wanted: either re-cut the note to phases 1, 2 and 3a and leave 3b to its own note once 3a's evidence exists (the note already routes that ordering), or name the channel that bounds space heat only, the envelope's owner and store, and both build sites.
9. harness, evidence plan gaps. "No fixture moves" is wrong for `tests/golden/config_flow.json`: `capture_config_flow` (tests/golden.py:1210) records the menu and every page, so a new page re-records it (not value-bearing, so the claim files stay untouched, as the note says). The README's page count and labels are pinned to `_OPTION_PAGES` (tests/entities.py:668-681), and the first conditionally created sensors need a `collect()` fixture with a list or they are never exercised (tests/entities.py:264-292). Fix wanted: name these three in "Evidence, by file".
