# R10-RCA-DEPENDABOT-STALE-HASH: Dependabot keeps the old hashes of a pin that a lock comment also names

Root-cause seat beside R10-DEPENDABOT-3414-COMPAT (`root-cause.md`), at
`origin/main` `d08ed31049`, 2026-11-11T01:32Z. No production code and no lock
edit. Instrument: `dev/audit/harnesses/dependabot_stale_hash.py` (this diff).

## 1. The defect, reproduced

Each grouped Dependabot pip pull request on `tests/` in round 10 carried pins
whose `name==version` line moved while the `--hash` block under it stayed the
previous version's. pip refuses such a pin (`THESE PACKAGES DO NOT MATCH THE
HASHES`, `tests / typing` job 129708149047 on #3414).

The census reads the pull request's head against its first parent, with no
network: a pin is stale when its version changed and its hash set did not
(distinct releases never share a sha256).

    python3 dev/audit/harnesses/dependabot_stale_hash.py \
      $(git rev-parse pr/3088 pr/3323 pr/3414)     # refs/pull/<N>/head

| pull request | head | pins moved (per file) | stale | stale pins |
|---|---|---|---|---|
| #3088 | `bffd45a03a` | 46 | 3 | coverage 7.17.0, cryptography 50.0.2, uv 0.13.6 |
| #3323 | `da3a5cfb8b` | 17 | 5 | coverage 7.17.2, acme 5.9.0, python-dateutil 4.0.0, sqlalchemy 2.1.8, uv 0.13.7 |
| #3414 | `4182e75d77` | 7 | 1 | homeassistant 2026.11.0 |

Exit 1 at each. The #3323 row is #3408's own list. Controls, the same command:
the re-apply lock commits `20fc628eee` and `b9c009a6b3` (#3147) and `a555d52ae8`
(#3408) read `stale=0`, exit 0; Dependabot's npm and github-actions heads in the
window (#3087, #3321, #3322, #3413) read `files=0 stale=0`, exit 0, as they
carry no hash lock.

## 2. The named cause

**A stale pin is exactly a pin whose `name==oldversion` also appears in a
comment of the same lock file, and Dependabot rewrote that comment.** Dependabot
replaces the version string at every match in the file, the comment included,
and the hash block of a declaration matched more than once is left unchanged.
The second half is inferred from the outcome: the seat did not read Dependabot's
updater source. The separation is measured.

- **Stale set = comment-rewritten set, in all three diffs.**
  `git diff -U0 pr/<N>^ pr/<N> -- 'tests/requirements*.txt' | grep -E '^[-+]\s*#'`
  prints for #3088 the `echo 'coverage==…'` regenerate line and the `<overrides>
  holds cryptography==…` and `uv==…` lines; for #3323 `coverage`, `uv`,
  `sqlalchemy`, `acme` and `python-dateutil`; for #3414 `installed lock:
  homeassistant==…`. Each set equals that pull request's stale set, pin for pin.
- **Null control: the pins not named in a comment.** Over the three pull
  requests 9 moved pins carry a comment occurrence of `name==oldversion` and 61
  do not; 9 of 9 are stale, 0 of 61 are. Hash count and publication date do not
  separate them (acme and python-dateutil have 2 hashes and went stale, anyio
  4.16.0 has 2 and did not; each of the 16 moved versions of #3323 and #3414
  queried on PyPI's JSON API was published at least 2 days before its pull
  request opened).
- **The boundary case agrees.** #3088's parent says `pyjwt==2.15.0.` (a full
  stop follows). Dependabot did not rewrite that comment and pyjwt 2.15.1 got
  fresh hashes.

The brief's hypothesis (the lock header compiles with hashes and Dependabot
runs no compile) is true and does not separate: all 70 moved pins share it, and
61 got correct hashes from Dependabot's per-pin path. The headers are
hand-written (`uv pip compile --no-header`), so no autogenerated-header
detection applies to any of them.

**Which side moved.** `git log --reverse -S` names who planted each comment:
`echo 'coverage==` by `cef18e0803` (#1548, 2026-09-24); `<overrides> holds
cryptography==` by `2ca7fb20e3` (2026-09-26); the `acme==5.8.0`,
`python-dateutil==3.0.0`, `sqlalchemy==2.1.6` and `uv==0.13.6` comments by
`20fc628eee`, and `installed lock: homeassistant==` by `b9c009a6b3`, both
#3147's re-apply of #3088 on 2026-11-01. Four of #3323's five stale pins and
#3414's one were planted by the previous re-apply; coverage's is #1548's
regenerate line.

## 3. The process state: (c)

The process exists and is quoted in `.github/dependabot.yml`'s pip entry: a pip
pull request is never edited, but re-applied by the lock header's compile. #3147
and #3408 followed it, and the census reads both re-applies clean. It did not
produce the intended result, a Dependabot pull request that installs: the
re-apply documents its overrides and holds in comments spelled `name==version`,
and that spelling is what makes the next Dependabot run leave stale hashes. The
process treated the staleness as random ("Dependabot leaves some hash lines
stale"), so no seat looked for what the stale pins share.

Not (b): nothing instructed the seats to keep pins out of comments. Not (d): the
Dependabot configuration and the lock layout were unchanged across the three
instances.

## 4. How far the class reaches

`python3 dev/audit/harnesses/dependabot_stale_hash.py --tree [<rev>]` lists the
precondition: every comment line naming a pinned package as `name==`. At
`d08ed31049` it prints `exposed=17` over 5 files (coverage, acme, aiohttp,
astral, cryptography, hass-nabucasa, homeassistant, orjson, pillow, pyjwt,
pyopenssl, python-dateutil, python-slugify, securetar, sqlalchemy, uv, yarl).
Each is stale-by-construction the next time Dependabot moves it.

Prediction against outcome, the moved pins named by `--tree` at each parent:
#3088 predicts coverage, cryptography, pyjwt, uv against stale coverage,
cryptography, uv (0 missed, 1 extra: the full-stop pyjwt, deliberately included
because the rule keys on `name==`, not on Dependabot's boundary); #3323 and
#3414 predict exactly their stale sets.

Elsewhere: the npm and github-actions ecosystems carry no `--hash` lines, so
the class does not reach them; the four Dependabot pull requests there read
`stale=0`. #3087 (actions) was also superseded, by #3160 and #3163, for its
allowlist, a different cause.

## 5. The cost test

`cost(countermeasure, recurring) < cost(defect) x P(recurrence)`, wall-clock per
occurrence.

**P(recurrence).** Measured: 3 of the 3 grouped pip pull requests in the window
(2026-11-01 to 2026-11-10) carried at least one stale pin, at one pip pull
request a week (`schedule: weekly`). Null control: 0 of 4 npm and
github-actions pull requests. With 17 exposed pins on main, the precondition
holds for next week too.

**cost(defect) per instance**, from the GitHub API (created, closed and merged
times; workflow runs listed per branch):

| instance | Dependabot PR red | re-apply | re-apply open | CI runs on the re-apply branch | review rounds |
|---|---|---|---|---|---|
| #3088 | 15 h 39 min, closed | #3147 | 7 h 49 min | 16 (4 cancelled) | 2, plus a budget raise |
| #3323 | 43 h 13 min, closed | #3408 | 1 h 26 min | 7 (2 cancelled, 1 failed) | 1 |
| #3414 | open, red from 15 min after opening | R10-DEPENDABOT-3414-COMPAT | open | | |

Automerge runs (`skipped`) are excluded from the CI counts. A lock change selects
`MODE: FULL`, so every counted run is a full suite.

**What the stale hashes alone cost.** None of the three would have merged with
correct hashes: #3088 needed a mypy budget raise, #3323 and #3414 need
homeassistant-stubs, zeroconf and cronsim held (triage batch 141, P543: 0 of 3
green under an ignore). So the measured saving over the window is 0 re-apply
branches. Stale hashes do add a cost the table does not show: the typing job
dies at `pip install --require-hashes`, so its mypy verdict, which is the
compatibility signal, is never computed on the Dependabot pull request, and the
re-apply seat sees it only after recompiling. In a week whose bumps are
otherwise compatible, the stale pin alone makes a re-apply necessary: 1 h 26 min
to 7 h 49 min, 7 to 16 full-suite runs and a review.

**Candidates.**

| candidate | recurring cost | removes the cause | verdict |
|---|---|---|---|
| A. no `name==` of a pinned package in a lock comment, guarded by `--tree` | the guard: 0.05 s per run (`time python3 … --tree`, real 0m0.052s); the rewording is one-off, inside a lock edit R10-DEPENDABOT-3414-COMPAT makes anyway (already `MODE: FULL`) | yes: 9 of 9 stale pins are its shape, 0 of 61 fresh pins are | **build** |
| B. lower pip schedule or `open-pull-requests-limit` (now weekly, 2) | fewer, larger groups | no: each instance still red, and a larger group moves more exposed pins | refuse |
| C. a workflow recompiling the locks on a seat-owned branch per Dependabot PR | one workflow run per pip PR, and a write-capable job compiling Dependabot-supplied content | the hashes only; 0 of 3 green (P543's compatibility reds remain) | refuse: A removes the same cause at 0.05 s |
| D. per-pin PyPI hash checker | | | refused by P544: 0 rounds saved |

A passes: its recurring 0.05 s per run is against a re-apply of at least
1 h 26 min in any compatible week, with the precondition measured present every
week.

## 6. Countermeasure

**Built in this diff:** the detector. `--tree` is shown to detect: exit 1 at
`d08ed31049` (17 exposed) and at #3414's parent `699f4d9ef4` (17), and exit 0 on a
scratch worktree of `d08ed31049` with `==` replaced by a space on every comment
line of `tests/requirements*.txt` (`exposed=0`, 2 files changed). The census mode
exits 1 at the three Dependabot heads and 0 at the three re-apply commits and the
four npm and actions heads. `--self-test` drives both modes over fabricated
text, a stale and a fresh pair and a commented and a prose-only header.

**Carried, not built.** This seat may not edit a lock, and a gate check landed
before the rewording would turn `main` red. R10-DEPENDABOT-3414-COMPAT edits
`tests/requirements-typing.txt` already and owns this:

1. reword every comment `--tree` lists so no pinned package is spelled
   `name==` (`name 1.2.3`, or point to the pin line; a regenerate recipe reads
   the version from the pin line, `grep -m1 '^coverage==' …`), and in the same
   diff correct `.github/dependabot.yml`'s "Dependabot leaves some hash lines
   stale" to name this cause;
2. run `dependabot_stale_hash.py --tree` from the suite that already reads the
   locks, so a re-apply cannot reintroduce the shape: exit 1 at its parent,
   exit 0 at its head, both runs in its body.

## 7. What this seat did not establish

- The Dependabot updater code path. The cause is the measured 9-of-9 against
  0-of-61 separation and the 1 boundary case, not a source reading.
- Whether a compatible pip week will occur. P(compatible week) is 0 of 3
  observed; the verdict on A does not depend on it, because A's standing cost
  is 0.05 s.
