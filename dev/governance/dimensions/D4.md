# D4 — UI/UX

Owner's brief: *"UI/UX — the card and the config flow, including grouping and
setup ergonomics. It should be intuitive, user friendly and look professional."*

Read `COMMON.md` first. Past rendering, your criterion is
`criteria/D4-criteria.md`, the file `dev/audit/config/objective.json` names
under `owner_criteria` for D4: a finding names the statement it fails.

## Method

1. **The card in a real browser.** Install Playwright from the browser lane's
   lock as `BASELINE.md` says; build the card as `tests/card_browser.mjs`
   does. The universe is every state `node tests/card_drift.mjs --list`
   prints times every language on the
   `language` row of `python3 tools/audit/check_scopes.py --repo . --population`;
   drive each at viewports 375×812, 768×1024 and 1280×800, light and dark,
   reduced-motion and coarse pointer. Then the released build's card in a
   real Home Assistant frontend (Limits). Measure with `getBoundingClientRect`
   and `getComputedStyle`: overlapping text boxes, text that overflows its
   box, WCAG AA contrast of every text/background pair, hit targets below
   24 px (44 px on the coarse pointer), keyboard tab order through every
   focusable, console errors, layout shift on hover. Screenshots go in your
   report directory.
2. **The config flow and the blueprints.** Drive every page through the stub
   the way `tests/entities.py`'s options loops do: field order and grouping,
   defaults, selector ranges, validation error keys and their translations,
   help text, and a value of the wrong physical kind typed into each numeric
   option. Score each page, and each `blueprints/` file's inputs, against
   `D4-criteria.md`'s F3, F4, I1 to I3, and count its fields. Count the
   steps from install to the first plan and what a new user must know at
   each.
3. **Professional look.** Consistency of typography, spacing and colour
   tokens across card states; legend and series colours across light/dark;
   alignment of headline numbers; empty and error states.

## Numbers

Pixels of overlap, contrast ratios, hit sizes, counts of fields and steps.
A finding says which state, which viewport, which element, and what a user
cannot do or read because of it.

## Reuse

`tests/card_rig.mjs` (`buildCard`, `planStates`, `qaTopologies`),
`tests/setup_qa_render.mjs`, `tests/golden/config_flow.json`.

## Limits to state

There is no Home Assistant frontend locally: config-flow rendering is
inferred from schema and strings, and step 1's real-frontend render runs
only on a recorded render from the owner's install or an instance the seat
stands up; without either, that input is `unfinished`. Say so in the report.
