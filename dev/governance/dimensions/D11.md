# D11 — Governance mechanisms and policy

Owner's brief: *"Governance mechanisms and policy — audited against public
golden standards, with the goal of upholding an effective and high-quality
LLM and coding process, as well as maintenance and improvement of the
governance structure itself."*

Read `COMMON.md` first. You read what the other dimensions are walled off
from: `main`'s history and GitHub's records — ruleset, check runs, reviews,
merged bodies. You audit the mechanism, never the verdicts it produced, and
leave cost and DORA's keys to `D13.md`.

## Method

1. **Inventory the mechanisms from the tree and the API, not from the
   index's account of them.** One row per refusal a seat can meet: the
   ruleset on `main` and each required check with the workflow job that
   produces it; each check class `policy_lint.mjs` prints when run;
   `brief_lint.mjs`; `tests/structure.py`; the claim files; `prepr.sh`; the
   hooks in `.claude/settings.json`. Per row: what it refuses, where it runs
   (branch, `main`, both), the positive control that shows it alive, and
   what it leaves uncovered. A mechanism whose control you cannot make fire
   is a finding.
2. **Score against public standards, one executed check per criterion**,
   with the standard's current text fetched rather than remembered and its
   own wording as the bar:
   - OpenSSF Scorecard (https://github.com/ossf/scorecard): run it, or
     evaluate a check by hand where the tool cannot see this repository.
     Report per check with its reason string — `Branch-Protection`,
     `Code-Review`, `Dangerous-Workflow`, `Token-Permissions`,
     `Pinned-Dependencies`, `CI-Tests`, `SAST`, `Maintained`,
     `Security-Policy`, `Signed-Releases` — and never the aggregate.
   - SLSA (https://slsa.dev), Build track: the level the release path
     meets — `tools/release/stamp.py`, the tag, the artefact — and what the
     next level would require.
   - OpenSSF Best Practices Badge criteria on change control, test policy,
     release notes and vulnerability reporting.
   - NIST AI 100-1 (the AI RMF), its GOVERN function, and NIST AI 600-1, the
     generative-AI profile, read for a process in which LLM seats author,
     review and merge: accountability (reviewer ≠ author provable from
     GitHub's records, not a comment's word), human oversight
     points, documented roles, defect and incident handling, measurement of
     the process itself. ISO/IEC 42001's continual-improvement clause is
     the bar for the second half of the owner's brief.
   - OWASP Top 10 for LLM Applications, current edition: prompt injection,
     improper output handling and excessive agency, applied to every place
     a job or a seat executes or obeys text it did not write — bodies a
     workflow reads, issue and comment text, a figure a job re-executes.
3. **Measure the structure's own health — the improvement half.**
   - Size and direction: `policy_lint.mjs --budgets` against its caps, and
     lines added per line deleted across the corpus over the window.
   - Detector health: each check class's control, on the acceptance and
     under `policy_lint_mutants.mjs`.
   - Recurrence: the friction histogram `policy_lint.mjs --stats` prints;
     a class at `orchestrator.md` section 3's root-cause threshold with no
     record beside it.
   - Conformance, sampled, with the sample and how it was drawn stated. Per
     merged pull request: a `Fix review: merge` verdict at the merged head
     from a seat other than the author; a first `pr-contract` run at that
     head that was green (the commit's check-runs, which keep a red run a
     summary drops); a disposition row; a red required check
     answered under `## Red checks`. One fraction per obligation.
   - Staleness beyond the `citations` class: decision status lines against
     the tree, handover traps, the files and steps the plan cites.
4. **Mechanise first** — owner's brief addition, tvofi 2026-10-24: *"each
   operation or shape that is not clearly a one shot and could be mechanical
   should be mechanical and wired into the machinery. This means reusable
   instrument before policy, only policy if no robust script could be built
   at a reasonable cost (tokens, time, complexity)"*. A finding is an
   operation recurring by hand, or as a prose step a seat executes, where a
   robust script was buildable at that cost: its recurrence count from a
   command run alone (`git log`, the step 3 histogram, a triage `Instances:`
   line), costed in `proposal-triage.md`'s terms with D13's per-merge
   figures, and sent there as a mechanisation proposal. An unused instrument
   under `tools/audit/seat/` is a conformance row; an operation
   `dev/programme/triage/` ruled is a finding only on a moved cost. A
   non-finding: a true one-shot, or a policy kept because no robust script
   exists, its binding reason recorded.
5. **Perturbation**, per `COMMON.md`: an emptied check, a body with one
   digit changed, one fixture instance added. Never on `main`, never against
   the live ruleset, never a comment on a live pull request; a perturbation
   you cannot run marks the finding `provisional`.

## Output

Beside `COMMON.md`'s report: the mechanism inventory; the
standards scorecard (criterion, standard, executed check, result, gap); the
conformance table; and a ranked list of changes, each with the standard it
moves and its cost in seconds per merge or lines of policy.
Severity: `critical` — a merge to `main` with no review or a red
required check, or a job executes text a seat did not write; `high` — an
obligation the record calls enforced that nothing enforces; `medium` — a
detector with no live control; `low` — hygiene.

## What has fooled people before

- The branch-rules endpoint is not bypass-aware: read the ruleset itself and
  probe it with both arms.
- A green mutation arm can be a mutation that never applied; drive the
  control by hand first.
