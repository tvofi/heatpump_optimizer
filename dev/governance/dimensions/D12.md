# D12 — Generalization

Owner's brief: *"the integration should be possible to use with a wide range
of setups and heat pumps."*

Read `COMMON.md` first. This is an audit lens, not a feature request. Do not
invent product surfaces. Judge whether the integration that already exists
stays usable across a range of plants, rather than only on a single
reference install.

## What you are hunting

An install the tree already claims to support — a hydronic layout, DHW or
no DHW, one zone or two, wood, solar, mapped sensors or a missing optional
entity, an on/off or modulating heat pump, a different control surface —
where setup does not complete, no plan publishes, the solver invents a
plant it was not given, or a required path crashes because that cell was
never the reference plant.

D8 owns per-entity sanity on the same matrix (state, unit, staleness).
D4 owns the card and config-flow UX of a given cell. D10 owns the quality-
scale rules. A finding that is only a wrong unit, a clipped label, or a
quality-scale miss is out of dimension; carry it rather than re-file it.

## Method

1. **Inventory the plant the tree already exposes**, from the options
   pages and the optional entity slots, not from memory. Cross it with
   `tests/golden.py` `coordinator_scenarios` (`coord_minimal`, `coord_dhw`,
   `coord_two_zone`, `coord_grid_fee`, `coord_all_features`) and the golden
   `SCENARIOS` that already toggle valve storage, wood, coil, two-tank and
   DHW. Derive the cell count; do not carry one.
2. **Installation axes.** For each cell: hydronic layout (single-zone,
   two-zone, wood-valve via `wood_share` at `thermal_model.py:1120`), DHW
   present or absent, wood present or absent, solar/PV present or absent,
   and every optional entity both mapped and omitted. Drive setup and one
   coordinator cycle the way `tests/entities.py` `collect` and
   `_capture_coordinator` already do.
3. **Heat-pump axes.** On/off versus modulating (the frequency map and the
   on/off climate path), and the control surfaces the tree already has
   (climate, number, switch, ECL110 MQTT, Tuya). A surface the tree does
   not implement is not a cell.
4. **Usable** means: setup finishes; a plan is published or a named
   refusal explains why not; no path invents a tank, a zone, a sensor or a
   compressor mode the config omitted; an omitted optional entity leaves
   its dependents unavailable or unused, not crashed. Count cells that
   fail that bar, and name the first failing step.
5. **Null control.** The same harness on the fully-mapped reference plant
   (`coord_all_features` and the richest golden). A failure that appears
   there is not generalization; name the dimension that owns it.
6. **Perturbation.** One omitted sensor, DHW dropped, wood dropped, PV
   dropped, or one zone removed: the fail-count must move. A harness whose
   number does not move when the plant shrinks is void.

## Reuse

`tests/golden.py` `coordinator_scenarios` and `SCENARIOS`,
`tests/entities.py` `collect` and `_honest_coordinator`,
`tests/features.py` `_t2_coord` / `_zone_coord`, `wood_share` at
`thermal_model.py:1120`, `tests/profiles.py`.

## Traps

- An omitted optional entity that correctly stays unknown or disabled is a
  non-finding. The finding is a crash, a fabricated value, or a plan that
  assumes a plant the user did not configure.
- Do not propose a new heat-pump protocol, a new hydronic layout, or a new
  entity the tree does not already have a slot for. Those are product
  requests, not audit findings.
- The reference plant passing every other dimension does not prove this
  one. The question is the cells that are not that plant.
