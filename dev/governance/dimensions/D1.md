# D1 — Robustness and stability

Owner's brief: *"Robustness and stability — lifecycle, staleness, executor
boundaries, store corruption, guards."*

Read `COMMON.md` first.

## What you are hunting

Ways the integration wedges, leaks, races, publishes stale or fabricated data
as measured, or turns a corrupt input into a permanent failure — under real
Home Assistant semantics, not the test stub's.

## Method

1. **A real-loop harness.** Subclass `tests/harness.py:FakeHass` so
   `async_add_executor_job` runs in a `ThreadPoolExecutor` on a real
   `asyncio` loop, and `async_create_task` schedules instead of closing.
   Then every lifecycle path, not one: setup → first refresh → reload
   mid-solve → unload mid-solve → setup again; an options update mid-solve; a
   service call during unload; remove; a restart onto persisted state. Per
   path and per line of `enumerate.py d1-lifecycle`, assert no live task,
   listener, timer or executor future references
   the torn-down coordinator (`asyncio.all_tasks`, `gc.get_referrers`), no
   exception escapes, and the new instance's first cycle completes.
2. **Store corruption fuzzing.** Every persisted payload
   (`enumerate.py d1-stores`; snapshots, ledger, learners, manual plan
   among them). Per store, at least 200 seeded mutants of the healthy
   payload: type swaps, missing keys, `NaN`/`inf`, negative or huge numbers,
   wrong nesting, truncation, strings where dicts go. Load through the real
   loader, run one cycle, assert it completes, the corrupt part is quarantined
   or reset with one log line, and the *next* cycle does not repeat the failure.
   Add one perturbation to the store-fuzz set: an instant written by a clock ahead of
   the one that reads it back, driven across a restart.
3. **Staleness.** Drive the watchdog and every "age" sensor under a frozen
   clock jumping forward/back, DST (`tests/hastub` `dt.freeze`,
   `tests/dst_checks.py`), `last_reported` in the future, `unknown` and
   `unavailable` states, a price list that stops updating and an empty
   forecast; check the published and booked value, not only the plan.
4. **Executor boundary.** From `_solve_record` and `_solve_hubs`,
   list every `self._*` the solve thread reads and every loop-side writer of
   them; a race harness mutates each writer mid-solve and checks the plan and
   the published payload for torn state.
5. **Guards, waits.** Each swallowing `try/except` (`enumerate.py d1-excepts`,
   every `broad` line): logs once, sets
   `last_update_success`, recovers, hides no bug? Inject it. Each peer wait
   (pipe, child, lock): a live, silent peer (`silent_peer_waits.py`) must
   time it out, freeing its hold, unless the wait is its own idle state.
6. **External-input parsers.** Each parse of input the integration did not
   produce — ECL110 MQTT, pump-signal states, the Tibber and Open-Meteo
   responses, the forecast — driven with malformed, non-finite, oversized
   and hostile payloads: the cycle completes, the failure logs once, the
   arm is pinned (#1090 pins ECL110's NaN drop; drive the rest).
7. **Upgrade.** Per `upgrade` line of `enumerate.py d1-stores`, and per
   earlier config-entry version through `async_migrate_entry`: a valid
   payload as that version's own writer wrote it (the package under
   `old-releases/<tag>/` in your export), never hand-built, loaded
   at the baseline and run one cycle beside a fresh install: same plan, same
   writes, nothing held that the fresh install releases. (v7.1.12 held a
   set-point write on a valid old payload; step 2 fuzzes corrupt ones only.)
8. **Redaction.** Every key `diagnostics.py` exports for a fully-mapped
   install, and every log call's arguments: plant a marker in each config
   field, location and entity id, then grep the export and the log. A marker
   that survives is a leak.

## Reuse

`tests/harness.py`, `tests/entities.py:_honest_coordinator`,
`tests/golden.py:_capture_coordinator`, `tests/hastub/homeassistant/util/dt.py:freeze`.

## Traps

`FakeHass` serialises the executor and closes coroutines. Real HA runs setup
and unload through the config-entry state machine, one at a time per entry; a
race reproduced only by calling a lifecycle method directly is a stub artefact.
