## P93: pulse --seat-queue prints UNREADABLE for every standing seat at every sweep (S6-V28)
Verdict: DEFER -> R10-ORCH-BEATD, which already owns the fix as P46's `--seat-alive` arm. Interim, no code: the orchestrator stops passing `--seat-queue` in its sweep and judges the seats by `<seat>.alive` age, as it already does. Making pulse accept the queues' format is REJECTED.
Source: s6 `proposals.md` `## V28`.
Instances: pulse at 20:09:44Z and 21:29:48Z both printed `seat-merge/roster/dispatch UNREADABLE: its queue could not be read`, from the orchestrator's account. This is the recurrence P46 (`s6-batch2.md`) predicted: "the same misreading is scheduled to repeat every sweep".
Cause, measured in the s6 queue files: `read_queue` in `tools/audit/seat/pulse.py` takes each non-blank line as `int(line.split()[0])`, so one non-epoch line makes the whole file UNREADABLE (`ValueError`). In the three queue files, counting non-blank lines whose first field is not an integer epoch:

| file | non-blank lines | non-epoch lines |
|---|---|---|
| `merge-queue.txt` | 35 | 11 |
| `roster-queue.txt` | 244 | 226 |
| `dispatch-queue.txt` | 9 | 2 |

The non-epoch lines are `#` header comments and ISO-8601 stamps such as `2026-10-24T07:50Z ...`.
The queues are also append logs. `judge_queue` assumes the seat removes a line when it acts ("an input the orchestrator queued and the seat removes when it acts"), but the roster queue alone holds 244 lines for the day. So even a format-tolerant reader would read every seat as STOPPED by its oldest line.
Cost: the interim costs nothing, one argument fewer in the orchestrator's sweep. The real fix is P46's: about 15 lines for a `--seat-alive SEAT=FILE[:MIN]` arm judged on the `.alive` mtime, plus fixtures and mutants. It is already carried into R10-ORCH-BEATD (the carry citing `s6-batch2.md#P46`).
Binding: the arm judges nothing today. It cannot raise a STOPPED, so a dead seat is caught only by the `.alive` age the orchestrator reads anyway; running it each sweep costs output and attention for no signal. Making `read_queue` accept `#` lines and ISO stamps is REJECTED: on append-log queues it would turn the false UNREADABLE into false STOPPEDs, and a false STOPPED makes the sweep restart a live seat (P46's worst case, a duplicate merge seat). Rewriting every seat's queue habit to remove acted lines is the four-seat contract change P46 already REJECTED on cost.
What would change the answer: R10-ORCH-BEATD waits behind R10-ORCH-DISPATCH-REG (not started), R10-POLICY-FIXER-MD (in progress) and R10-ORCH-REVIEW-PACKET (not started), on the roster branch. If the orchestrator wants the alive arm before those land, P46 already named the split: item 2 alone as an XS group (`pulse.py`, `INSTRUMENTS.md`) after the drain, carrying P46's text unchanged.

## P94: a git or gh read from a non-repo cwd reads blank and is reported as a state (S6-V29)
Verdict: ACCEPT NARROWED. (a) The one in-tree cause, the sweep template's unpinned `git ls-remote`, is a carry into R10-ORCH-BEATD, which owns `tools/audit/seat/sweep_template.md` under P45. (b) The out-of-tree cause, the roster seat's pass script, gets a no-code fix: the orchestrator edits its seat scripts. A general fail-closed wrapper for every read is REJECTED.
Source: s6 `proposals.md` `## V29`.
Instances: 2, from the orchestrator's account:
- The orchestrator's 23:49Z sweep ran `git ls-remote origin ...` from the r10s6 state directory and got "'origin' does not appear to be a git repository", so the probe and handoff refs went unread that sweep.
- The roster seat's pass script (w12) ran `gh pr view` outside a repository, got blank results, and for several passes reported #2761 and #2767 as "OPEN" without a real read.
Cause, read in the tree and in the s6 files:
- (1) `sweep_template.md` step (2) says to compare `git ls-remote --heads origin 'handoff/r{{round}}-*'` with the open heads, with no `-C`. Step (0) of the same template already pins `git -C {{orch_checkout}}`, so the placeholder exists and step (2) simply does not use it. The rendered s6 sweep line 9 carries the same unpinned command.
- (2) The s6 `roster-pass.sh` line 9 reads `s=$(gh pr view $n --json state,mergedAt ... 2>/dev/null)`. That has no `--repo`, so it depends on the cwd. Its errors are discarded, so a failed read is an empty string that the script then reports.
The in-tree instruments already pin and fail closed: `pulse.py` and `orchestrator_tick.py` take `--repo` and print UNREADABLE for an input they could not read. Both instances are prose or hand-written scripts, not instruments.
Cost:
- (a) One placeholder in one template line (`git -C {{orch_checkout}} ls-remote ...`), plus a `sweep_render.py` fixture row asserting that every `git ` command in the rendered sweep carries `-C`. The rendered sweep's other git and gh lines go through instruments.
- (b) Two edits to the out-of-tree `roster-pass.sh`: `--repo tvofi/heatpump_optimizer`, and a non-zero exit or an empty answer prints UNREADABLE in place of a state word. It is not in the tree, so it needs no PR.
Binding: each instance cost a sweep's refs or several passes of false state, and both causes are one line each, so the narrow fixes clearly pay. A general wrapper that every seat script must call for every git and gh read is REJECTED: the instruments already fail closed, and a wrapper binds only the scripts that remember to use it, so it would add a file without closing the class for hand-written scripts. The fixture row is the mechanical part for the template. For out-of-tree seat scripts, the standing rule is the one `INSTRUMENTS.md` already gives: use an instrument before hand-rolling a read loop.
What would change the answer: a third instance in a hand-written seat script after (b). That would mean seat scripts need an instrument, a read-only `--repo`-pinned state reader. Re-rule then.
Carry text (for `roster_edit.py append-carry R10-ORCH-BEATD`, citing `triage: dev/programme/triage/s6-batch20.md#P94`): "tools/audit/seat/sweep_template.md step (2): pin the handoff listing to the orchestrator's checkout, `git -C {{orch_checkout}} ls-remote --heads origin 'handoff/r{{round}}-*'`, as step (0) already does with `-C {{orch_checkout}}`. Evidence: the 2026-10-24 23:49Z sweep ran it from the state directory, got \"'origin' does not appear to be a git repository\", and read no probe or handoff refs that sweep. Controls: a tools/audit/seat/sweep_render.py fixture row asserting that every `git ` command in the rendered sweep carries `-C` (null: the old step (2) text fails the row); one mutant drops the `-C`."

## P95: a third blank-read instance in a hand-written seat flow, re-ruling P94 (S6-V29, instance 3)
Verdict: ACCEPT (barrier) -> R10-ORCH-BEATD (carry; it owns the `standing-*.md` contracts under P45). Each standing contract names the cwd-safe instrument for each read its seat makes, and says a hand-written pipeline is never a check. Interim, no code: the orchestrator adds the same lines to its out-of-tree seat briefs now. P94's "read-only state reader" fallback is REJECTED, because measurement shows the readers already exist. A harness hook that refuses unpinned `git` and `gh` commands is also REJECTED.
Source: s6 `proposals.md` `## V29 instance 3`; P94's own re-rule clause (a third instance in a hand-written seat flow).
Instances: 3 in one day, all in hand-written seat flows: the 23:49Z sweep's unpinned `git ls-remote` (P94 (a)); the roster seat's `gh pr view ... 2>/dev/null` (P94 (b)); and, at 00:31Z, dispatch seat w22's #2772 body check, run from the wrong directory, which returned a false 0 (clean) before it was redone from the worktree. The dispatch report does not record which command returned the 0; the orchestrator's entry is the source. That is the third instance, so a barrier is owed, not a note.
Measured, with the s6 batch-20 worktree's tools run from an empty scratch directory outside any repository:
- `node tools/policy/policy_lint.mjs --pr-body <body> --head <sha> --base <sha>` still judged the body (it found the stale `## Head` error it should).
- `python3 -I tools/audit/carry_audit.py check --body <body>` still reported a seeded bad destination: "1 bad destination(s)", identical to the same run from the worktree.
- A hand-written pipeline in the same directory, `git diff --name-only origin/main...HEAD | wc -l`, printed `0` with exit 0. That is a false clean of exactly V29's shape.
So the instruments a seat should use are already cwd-safe, and the false states came only from hand-written reads. The common cause is the harness itself: each Bash call starts in the seat's original directory (a `cd` in one call does not reach the next), so a relative path or a bare `git` or `gh` reads whatever directory the call happens to start in.
Cost: prose only, about one line per standing contract plus a line in the orchestrator's seat briefs. For each read, it names the instrument: for a PR body, `policy_lint.mjs --pr-body` and `carry_audit.py check --body`; for a PR's state, a `gh pr view --repo tvofi/heatpump_optimizer` read that prints UNREADABLE on a non-zero exit or an empty answer; for handoff refs, `bus.sh orphans` or `git -C <worktree>`. It also adds the rule that a count piped from `git` or `gh` (`| wc -l`, `grep -c`) is never a check result. No new file and no API cost.
Binding: three false states in a day, one of them a false clean on a body check that gates a review, against a few lines naming instruments that already pass from any directory. The barrier is the contract naming the instrument for each read, which makes a hand-written read a contract breach that a reviewer can name, rather than a habit to remember.
- The REJECTED reader would duplicate `policy_lint` and `carry_audit`, which already fail correctly outside a repository.
- The REJECTED hook (a PreToolUse check refusing a `git` without `-C` or a `gh` without `--repo`) would have to parse compound shell commands and the directories they `cd` into. That is a predicate built from three failures, which over-fires on every legitimate read inside a worktree, and a harness setting is the owner's to change.
What would change the answer: a fourth instance after the contracts name the instruments. A seat then broke a stated contract line, which is a review finding on that seat, and the hook question can be re-opened with that evidence.

## P96: merge_pr.sh has no carry path for a carried single (S6-V30)
Verdict: ACCEPT NARROWED. `merge_pr.sh --carry` is REJECTED: a carried single merges through `tools/audit/seat/merge_train.py`, which already carries.
- (a) Carry into R10-FLOW-POSTMERGE, which lists `tools/audit/seat/merge_pr.sh` in its hot files: when the reviewed SHA in the verdict is not the PR head, `merge_pr.sh` refuses before posting anything and names the route, a one-entry `merge_train.py run` queue. It gets no carry logic of its own.
- (b) Carry into R10-TRAIN-UPGRADE arm (3), adding a PR to a running train: its test includes a carried single, whose verdict is at an ancestor head, added to a live train and landing at that train's next batch.
Source: s6 `proposals.md` `## V30`. Instance: #2762, carried from c851f2a8 to 2f5bf725 (`app_approve.sh --carry` gave `CARRY: yes`; claims empty; budget-raise-gate green). `merge_pr.sh` re-posts the verdict, and `app_comment.sh` refuses a merge verdict whose SHA is not the live head (its step 12). So the single waited for the live train, about 1 h or more.
Instances: 1 (#2762).
Measured on main:
- `merge_pr.sh` already routes queues to the train: "For a queue of verdicted PRs, merge_train.py does the same with recarry and the carry check".
- `merge_train.py`'s `at_head` runs `app_approve --carry <verdict> <head>` on every entry and lands on `CARRY: yes`, and admission does the same. A one-entry `run` queue whose `verdict` is c851f2a8 therefore carries #2762 with no new code.
- `train.sh` refuses only a second train on the same state directory.
The candidate's benefit is therefore only a merge beside a live train, and that saves nothing overall. A single landed beside a live train moves main under that train. The train then pays a main-moved recovery, a full CI wait at the new head of about 40 min (the `MAIN_MOVED_TRIES` comment), up to three times. The single's wait is not removed, only moved onto every entry in the batch.
Cost:
- (a) One comparison, the verdict SHA from the evidence directory's verdict file against `S`, before `app_comment.sh` posts anything, plus one self-test case. A carried head refuses with a CARRIED HEAD line naming the train route; the null control, an equal SHA, posts as today. About 10 lines in a file R10-FLOW-POSTMERGE already edits.
- (b) One test case in a group already in progress.
- The candidate would cost a second carry path beside `merge_train.py`: approval at the moved head, the policy gate, the row check, and the carry refusal classes. Every later carry fix would then owe two edits.
Binding: the train is the one carrying merger, by its own design and `merge_pr.sh`'s own comment, so a second one is duplication that pays nothing back. The real slip was that `merge_pr.sh` refused late, after reading the verdict, with a message that did not name the route; (a) fixes that. The remaining wait, a single behind a running train, is exactly what R10-TRAIN-UPGRADE arm (3) is building, so (b) makes sure arm (3) covers it.
What would change the answer: a carried single the train refuses but `app_approve.sh --carry` accepts. That would be a train defect, owed to R10-TRAIN-UPGRADE, not a reason for a second merger.
