## P86: every train merge is refused twice before it lands (S6-V21)
Verdict: ACCEPT -> R10-TRAIN-UPGRADE (carry; the same `merge_train.py` seam it is editing now, so no separate group): approve each entry ahead of its merge, overlapping the review-event CI run, and never post a second approval at an unchanged head.
Source: s6 `proposals.md` `## V21`.
Instances: 3, measured. In s20's train log, #2741 and #2710 each show "merge attempt 1/8 refused" and "2/8 refused" with GitHub's "the base branch policy prohibits the merge", then MERGED on attempt 3. #2709 shows the same in the orchestrator's account (approved 19:15:14Z, merged 19:16:55Z).
The cause, measured. V21's hypothesis was a mergeability recompute. The workflow-runs listing for `event=pull_request_review` shows something more concrete: every approval starts a `CI review pr=<n>` run of `ci.yml`, which `ci.yml` triggers on `pull_request_review: [submitted, edited, dismissed]`, and whose jobs (among them `budget-raise-gate`, which re-reads the approval by design, and `refresh`) report at the head. The merge is refused until that run concludes:
- #2709: approved 19:15:14Z; review run 40124449022 ran 19:15:17Z to 19:16:23Z (66 s); merged 19:16:55Z.
- #2741: approved 20:28:40Z; review run 40129950489 ran 20:28:43Z to 20:29:57Z (74 s); merged 20:30:32Z.
- #2710: review run 40130190054 ran 20:31:49Z to 20:33:05Z (76 s).
The rest of the gap is the merge loop's grain. `land` in `tools/audit/seat/merge_train.py` sleeps 30 s before every attempt, the first included, so a run of about 70 s costs two refused attempts and lands on the third at about 90 to 110 s. That matches V21's 1.7 to 1.9 min.
A second waste rides the same path. `app_approve.sh` POSTs a new review on every call, with no check for an approval already at the head, so a re-prove that re-enters `land` re-approves. #2741 was approved twice in s20 (before and after its `[MAIN-MOVED]` re-prove). That started a second review run, 40127491988 (created 19:55:36Z), and the merge then waited on the newer one.
Cost: S inside R10-TRAIN-UPGRADE, about 20 to 30 lines in `merge_train.py`, plus self-test rows and a mutant. No new file, no standing cost, and one fewer GitHub write per re-prove.
Risk: low. The approval is the same `app_approve.sh` approval at the same head under the same gates; only its timing moves earlier. Its gates (carry, evidence, CI at the head) are read at admission, when the head is already fixed. A head that moves after admission still needs a fresh approval at the new head, which the dedupe must not suppress.
Binding: about 1.8 min of serial train time per merge (V21's figure is about 70 min a day at about 40 merges), plus one extra review CI run per re-prove, against about 25 lines in a function the owner-ordered upgrade is already rewriting. A separate group would collide with R10-TRAIN-UPGRADE on the same `approve` and `land` lines, which is why this is a carry into it. Polling `mergeStateStatus` alone is rejected as the main fix: it trims only the 30-s grain (about 20 to 40 s) and still serialises the review run (about 70 s) behind each merge. As the merge loop's wait, it is a fine secondary measure.
