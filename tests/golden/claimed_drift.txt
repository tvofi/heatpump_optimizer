# Scenarios this branch deliberately moves, one name per line, reason after
# the hash. env_drift.py prints their diffs but does not fail on them; a
# stale claim (a listed scenario that did not move) DOES fail, so entries
# cannot outlive the PR that needed them. It fails in its own right, under
# its own heading: nothing drifted, the list is just out of date. Empty
# list = this branch claims byte-identical behaviour everywhere.
#
# A claim describes exactly ONE diff and never carries forward. Two rules
# enforce that, and a branch must satisfy both:
#
#   1. The `claims-for:` line below is machine-read and MUST equal the
#      repo-root VERSION file. Both tests/env_drift.py (before any capture,
#      in either mode) and tests/entities.py fail when the two disagree.
#   2. In `--all` mode the list below must DIFFER from the baseline's --
#      the same names with the same reasons mean it was written for the
#      baseline's diff, not this one, and env_drift.py fails the run. The
#      stamp cannot catch that on its own: it only expires claims when
#      VERSION changes, and merges at an unchanged version are common here
#      (7b512bc, 401db6e and 2248f64 all sit at 4.0.0). An empty list is
#      always fine -- it claims nothing.
#
# So this file is rewritten by every change that touches it, and a release
# that moves no goldens still restates its own footprint: bump the line,
# leave the list empty. Without rule 1 the file is committed and inherited:
# v4.0.7, v4.2.0 and v4.3.0 each moved nothing, inherited the previous
# release's claims, and failed CI on main with N stale claims for code that
# was never wrong. Without rule 2 the same thing happens whenever two
# commits share a version.
#
# Two categories live in this file.
#
# A CLAIM is a bare scenario name with a reason after the hash. It asserts
# that THIS release moves that fixture, it is checked both ways (unclaimed
# drift fails, and so does a claim nothing matched), and it expires with the
# `claims-for:` stamp below.
#
# A MAY-DRIFT entry is a comment line, `# may-drift: <name> -- <reason>`. It
# asserts nothing: the fixture moved here, or it did not, and either is fine.
# It exists only for the five fixtures this gate itself declares
# non-reproducible across BLAS builds, and env_drift.py refuses any other
# name -- see `_may_drift` there for the full reasoning. Because it is a
# statement about those fixtures rather than about one release's diff, it
# does not expire with the stamp and is not part of the inherited-claims
# comparison.
#
# claims-for: 5.1.8
#
#
# v5.1.8 — the DHW charge limit stops being the disinfection temperature.
# `dhw_max_temp` was `max(setpoint, legionella_temp)`, so the cost planner had
# a 60 °C ceiling to spend on every ordinary day and spent it: the stock 55/60
# defaults ran the tank to 59.16 °C with no cycle due, and the reporting
# owner's 52/60 pair ran it to 58.39 °C. The ceiling is now the user's charge
# limit, raised per step only around a cycle the planner actually placed. Every
# fixture that plans hot water therefore moves, and the peaks all land on the
# charge limit: 59.16 -> 55.00 on the stock defaults.
#
# The direction of the COST is worth stating plainly, because it is not the
# one you would guess: hot water generally costs a little MORE, not less
# (winter_single_dhw 7.03 -> 8.19 SEK of DHW, whole-plan 29.17 -> 30.35). The
# over-charge was not waste, it was arbitrage — the ceiling was the storage
# headroom the plan used to carry cheap night electricity into the evening,
# and honouring the user's limit gives some of that up. Energy falls, price
# paid per kWh rises. Fixtures whose tank never reached the old ceiling
# (dhw_large_tank) barely move.
#
# Three further movements ride along, all consequences of the same split:
#
#   * `_repair_dhw_floor` was the one planning stage with no ceiling of its
#     own. It ran after the capacity clamp and was bounded only by the model's
#     tank-rating clamp — which stopped bounding it the moment the charge limit
#     and the rating became different numbers. It is bounded per step now, as
#     far as the breach it is closing; past the breach the ceiling is ENFORCED
#     by clamping the tail, because heat the tank has no room for later is
#     refused rather than stored. (Stating the bound over the whole tail
#     instead made every later step sitting ON the limit read as zero room,
#     and a suffix-minimum carried that zero back over every earlier
#     candidate, so the repair refused every top-up there was.) On the
#     legionella-off configuration this alone takes the published schedule
#     from 13.34 to 6.53 kWh — for the same 55.00 °C peak, the same 54.17 °C
#     end state, and the same heat actually delivered: of the thermal energy
#     the old plan asked for, 16.70 kWh of 21.58 was refused by the tank,
#     against 6.20 of 11.07 now. 4.88 kWh went in either way. What changed is
#     that the plan no longer publishes power the tank will not take.
#   * `_clamp_dhw_to_capacity` sized its allowance from the temperature rise
#     alone, ignoring the draw and the standby loss the same step also has to
#     pay for, and measured its headroom at the step's START. It is exact
#     against the simulation it protects now, so a truncated step lands ON its
#     ceiling instead of a fraction below: 54.91 -> 55.00 in every fixture
#     whose tank charges to the limit, and a disinfection ramp reaching 60.00
#     where it used to stop at 59.90.
#   * an overdue disinfection cycle no longer collapses to step 0, and whether
#     the tank can reach the disinfection temperature at all is simulated
#     rather than estimated from lift ÷ rate. `legionella_due` (170 h) and
#     `everything_on` (160 h) both move their cycle.
#
# The reason codes and the battery slab ceiling that moved fixtures in v5.1.7
# are untouched here; every scenario below moves because its hot-water plan
# does. Space-only fixtures (dhw=False) are byte-identical and are not listed.
#
