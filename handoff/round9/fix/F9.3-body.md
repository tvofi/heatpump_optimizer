Round-9 F9.3: the P1 declared-domain barrier (card C1). Arm 4 refuses a stored
value that is poisoned or absurd in magnitude. It could not refuse a finite value
outside the domain only its writer knows (a duty of 1.5, a decile of 12), nor a
loader that drops a whole valid grid for one bad cell. This PR closes that gap.

- **`store.DOMAINS`** (in `store.py`, borrowed from F1) declares, for every
  stored field of all 13 stores, the domain its own update path writes. Where
  the owning module names a bound, the table imports that constant. The one
  exception is the DHW profile ceiling: `dhw_learning` imports the store, so the
  ceiling is a literal, held equal to the module's own value by an Arm 6 check.
  Snapshots alias the learner payloads they carry. The table only declares;
  enforcement stays in each loader. `QuarantiningStore.async_load` logs, at
  debug level, any field that is undeclared or off its declaration. A loader
  that keeps an opaque record whole (the month receipts, the score day, the
  fuse advisor, a snapshot's accuracy summary) now admits it only when every
  field lies inside its declaration (`store.admitted`), and drops it otherwise.
- **Arm 6** (`tests/finite_boundary.py`) builds a rich seed through the real
  savers, so every section a saver can write is populated with distinct values.
  It then runs four checks. **Coverage:** every leaf and map key is declared,
  and a planted undeclared field is refused. **Out/in:** each bounded field or
  key is substituted just outside its domain and freshly inside it, run through
  the real loader, and re-saved by the real saver. Nothing out of domain may
  come back, and the in-domain value must round-trip, so the out-probe is not
  vacuous. **Blast radius:** one bad cell per grid may cost only that cell,
  unless the declaration names the grid `whole` and gives the reason.
  **Null control:** the healthy seed round-trips unchanged. For the snapshot
  store, the check restores the ring and re-saves every learner store the
  restore wrote.
- **Loader fixes** for what Arm 6 found at the base, in each seam's own house
  style:
  - Counters are floored, or dropped below one when a fold writes one:
    `cop_samples` and three siblings through `_storable_sample_count`,
    `cooling_samples`, `overrides`, the lead counts, the starts months and the
    ledger meta counts.
  - The comfort `learned_weight` gets its update path's clip, and the CUSUM
    statistic is capped at the detector's own cap.
  - A `[value, samples]` fold with a non-positive value or no sample is dropped
    (`_learned_pair`: `capacity_envelope`, `cop_baseline`).
  - Non-negativity is enforced for draw reservoirs, the internal-gains profile,
    the aperture fit's `n`/`mx`/`var` (`_at_least`) and a sample's predicted
    power.
  - The opaque records named above are admitted only in domain.
- **The F3.3 float lead.** Four `float()` sites can receive a Python int too
  large for a float, fed by entity attributes and a service field, and each now
  catches `OverflowError`: `coordinator._as_float`, `freq_control._finite`,
  `inputs._finite` and `wood_fuel._wood_slots_error`. A fifth, `accuracy.py`'s
  sample parser, got it with the domain fix it shares a line with. The other 36
  are unreachable (Figures).
  - Correction to the recorded design, decision 4: the store boundary did not
    need widening. `_poisoned("1e999")` is already True, because `float()` of a
    string returns inf and never raises `OverflowError`, and a huge int is
    refused by the magnitude branch. orjson, which Home Assistant uses to parse
    storage, config entries and HTTP, never yields an int too large for a
    float: it parses ints wider than 64 bits as a float, and raises beyond a
    float's range.
