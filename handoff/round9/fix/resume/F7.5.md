  two English catalogues are not pinned to each other.** `tests/entities.py:123`
  resolves entity names through `strings.json`; the archscore `family_splits`
  enumerator (`a3/metrics/family_splits.py:load_rows`) reads
  `translations/en.json`. Nothing compares the two `entity` sections
  value-for-value, and the gate does not notice when they disagree. Measured,
  both arms, in a detached worktree at head (harness:
  `/private/tmp/audit-7/f7-5/seam_probe.py` and `seam_probe2.py`; the five-lane
  arm takes about four minutes):

  | arm (one file reverted, the other left) | result |
  |---|---|
  | `strings.json` only | `tests/entities.py` rc 0 → 1; new red: `every declared family sorts as one contiguous run in en and sv (#1760)` |
  | `translations/en.json` only | rc unchanged; **0 new reds** in `entities`, `features`, `doc_claims`, `config_flow_steps`, `deployment_shape` |

  Upstream hassfest's `validate_translation_file`
  (`home-assistant/core` `script/hassfest/translations.py`) validates **each**
  file against the generated schema and never compares their values, so the
  `Hassfest` job does not close it either. The suite's only two
  `strings.json`-vs-`en.json` parity checks — `features.py:19907` and
  `features.py:30881` — both read `.get("exceptions", {})`, so they cover the
  exceptions section and nothing else.

  instruments.** This PR did; it is not guarded, and a seat that edits one file
  will keep the gate green while the enumerator and the shipped translation
  disagree.
