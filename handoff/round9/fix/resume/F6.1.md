## Round 2: review response (folded into this chain)

The originally blocked commit (`e6d48bf`) keyed D4-s1-01's dark colours off
a CSS `prefers-color-scheme` media query (the OS setting) rather than
`hass.themes.darkMode` (HA's own profile setting, independently settable),
and its restored "dark" literals deferred to `var(--error-color, ...)`,
which HA's real dark theme sets to `#db4437` — only 3.97:1 on `#1c1c1c`,
not AA-safe. Fixed by computing `darkMode` in JS and giving dark mode its
own dedicated, independently-verified literals (`*_READABLE_DARK`).

D4-s1-03's fix in that commit (`uniqueHeadLen`/`pickerLabelIds` v1) kept a
computed head before an internal ellipsis, sized to disambiguate among the
*ids on screen as strings* — this passed `tests/card.mjs`'s own string-only
checks, but the real-browser P9 grid (`tests/card_browser.mjs`, real
`canvas.measureText()` against the option's actual computed font) proved it
insufficient: this project's own default space/DHW plan-sensor ids share a
prefix and suffix long enough that the real pixel-width clip lands before
v1's internal ellipsis marker, so both options rendered as the same visibly
clipped text (`select.sp-select "sensor.heat_pump_optimizer_pla"`). Fixed
by replacing the scheme with a front-stripping one: an id whose prefix
collides with a sibling's (`commonPrefixLen` >= 12) has that shared run
stripped from the front and replaced by a single leading `…`, so the
differentiator sits immediately after it regardless of where an unknown
clip width lands.

## Round 4: carry brief correction

An independent review of round 3's carry (code head `8077efe`) found one
passage in `carry-1652.json`'s `brief` wrong: it told F6.3 to drop two
"theme vs OS mismatch" grid cells as describing a state HA cannot reach.
That is backwards. `hass.themes.darkMode` is a profile setting the HA user
sets themselves, independent of the OS's own light/dark preference -- HA
dark mode on a light-OS machine (or the reverse) is an ordinary install,
not an impossible one. Those mismatch cells are in fact the only thing
that would catch the card's colours ever being keyed off the OS again
(exactly the bug D4-s1-01 fixed). Corrected in commit `8f4962c`: the
brief now tells F6.3 to keep two OS-mismatch cells (HA dark on an OS
light scheme, HA light on an OS dark scheme), each with `darkMode` and
the theme CSS vars in lockstep with each other (HA's own state) while the
OS axis is set to the opposite -- alongside the normal, non-mismatched
lockstep cells the brief already asked for. No other content changed:
the measurement (8 contrast failures unpatched, 0 patched), the code, and
every figure below carry over from round 3 unchanged.
