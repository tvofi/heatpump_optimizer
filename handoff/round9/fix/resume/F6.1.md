## Round 2: review response

The blocked commit (`e6d48bf`) keyed D4-s1-01's dark colours off a CSS
`prefers-color-scheme` media query (the OS setting) rather than
`hass.themes.darkMode` (HA's own profile setting, independently settable),
and its restored "dark" literals deferred to `var(--error-color, ...)`,
which HA's real dark theme sets to `#db4437` — only 3.97:1 on `#1c1c1c`,
not AA-safe. Fixed by computing `darkMode` in JS and giving dark mode its
own dedicated, independently-verified literals (`*_READABLE_DARK`).

D4-s1-03's fix in that commit (`uniqueHeadLen`/`pickerLabelIds` v1) kept a
computed head before an internal ellipsis, sized to disambiguate among the
*ids on screen as strings* — this passed `tests/card.mjs`'s own string-only
checks, but the real-browser P9 grid (`tests/card_browser.mjs`, real
`canvas.measureText()` against the option's actual computed font) proved it
insufficient: this project's own default space/DHW plan-sensor ids share a
prefix and suffix long enough that the real pixel-width clip lands before
v1's internal ellipsis marker, so both options rendered as the same visibly
clipped text (`select.sp-select "sensor.heat_pump_optimizer_pla"`). Fixed
by replacing the scheme with a front-stripping one: an id whose prefix
collides with a sibling's (`commonPrefixLen` >= 12) has that shared run
stripped from the front and replaced by a single leading `…`, so the
differentiator sits immediately after it regardless of where an unknown
clip width lands.

Both fixes were verified against the ACTUAL Home Assistant behaviour, not
just re-reasoned: HA's real light/dark theme CSS-variable values
(`tests/card_browser.mjs`'s `THEMES`) for the contrast math, and a real
Chromium's own text-clipping measurement for the picker labels.
