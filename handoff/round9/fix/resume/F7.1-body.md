Why this change, and what it measures.

`hvac_action` gated on `coordinator.data.get("mode")` before checking whether
the pump was actually running. `boost.overlay()` sets
`heat_pump_on`/`power_normalized` on the current action independently of
`self._mode` (its own docstring: the boost channels "do not stomp comfort or
economy the way selecting the global boost mode does"), so a space or DHW
boost run while the optimizer mode was "off" reported `hvac_action=OFF` while
the pump ran (D8-s2-02, class P2). The running action is now checked first.

That same stale-payload read also disagreed with `hvac_mode` above it, which
already reads the live `coordinator.mode`: `async_set_mode` flips `self._mode`
at once, but `coordinator.data["mode"]` only catches up once the refresh a
mode change asks for has run its solve, so the two properties on one entity
could show a mode-off/heating split for that window. `hvac_action` and
`OptimizerEnableSwitch.extra_state_attributes["mode"]` (which had the same
stale read next to `is_on`'s live one) now both read `coordinator.mode`
(D8-s2-03, class P2).

D1-s3-04 (#1683, class N-shared-config: the climate entity's
`target_temperature` reads `coordinator.target_temperature`, which returns
`_opt_config.target_temp` live; `away.apply_setback` mutates that same
`_opt_config.target_temp` for the duration of `async_run_optimization`'s
executor-scoped solve, so a concurrent read during that window sees the
away/peak-guard setback rather than the user's configured target) is **not
fixed in this PR**. The class sweep's proposed fix (publish
`target_temperature` from the per-cycle `coordinator.data` snapshot, the way
every other entity here already reads it) needs a `coordinator.py` change,
outside this lane's owned files (`climate.py`, `switch.py`); per this lane's
own brief ("if the fix needs coordinator.py or away.py, stop and hand that
part to F1 or F3 rather than borrowing"), it is reported here rather than
borrowed. `Part of #1683`.
