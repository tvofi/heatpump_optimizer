## Design correction (seat 3, 2026-09-30)

Decision 4's premise is false, measured at a15e3e33: `_poisoned("1e999")`,
`_poisoned("-1e999")`, `_poisoned("9"*400)` and `_poisoned(10**400)` are all
already True. `float(str)` never raises OverflowError (it returns inf, which
the non-finite branch refuses), and a huge int is refused by the magnitude
branch. So the store boundary ALREADY refuses every store-fed OverflowError;
there is nothing to widen, and "1e999" in `_A4_STR` would pin existing
behaviour, not a widening. OverflowError from `float(x)` needs a Python int
beyond a double; orjson (HA's storage, config-entry and HTTP JSON parser)
never yields one (it parses ints beyond 64 bits as a double and refuses
beyond a double: measured, `orjson.loads("1"+"0"*400)` raises
JSONDecodeError). The float-site work is therefore a per-site reachability
disposition (entity attributes and stdlib-json payloads can carry such an
int), not a boundary widening. The lead's 29-site rule was not recorded; this
seat's rule is `floatsites.py` (AST: a float() call in a try whose handlers
catch TypeError or ValueError but none of OverflowError, ArithmeticError,
Exception, bare except), 41 sites in 19 files at a15e3e33.

Oracle choice for Arm 6: "held live" is measured as what the store's own
saver writes after the loader ran (load, then save, then check every leaf
against DOMAINS). The live model is what the saver serializes, so an
out-of-domain value held live is an out-of-domain value re-saved.
