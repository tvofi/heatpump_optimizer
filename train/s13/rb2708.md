cause is not the no-remote shape. It is the live required-status-check

for a fixed ruleset. The defect is in the instrument: an exit-code row printed

**The cause, from CI's own logs.** All in the window 2026-10-22T13:45–13:52Z

The two env-matrix jobs failed different arms. Each arm runs its own
`policy_lint` process, and each process reads the ruleset once
(`counts.mjs` `liveRequiredContexts`, memoised per process). So one job's
arms can sample a ruleset edit at different moments. The no-remote mutants
row fails whenever its arm's `policy_lint` exits 1: the lane prints
`MUTANTS: the entry point exited 1 on the corpus as it stands`. One cause
therefore fails both no-remote rows.

**Reproduced in CI's shape** with the new harness
`dev/audit/harnesses/r10_envmatrix_noremote.sh`. It builds a full clone at the
head with origin/main at the base, runs the job's own "Restore the check
source" step (read from governance.yml at the head), commits it, and runs the
driver that checkout holds. The four runs at 97ac438d6 over base 4714748
(`## Figures`):
- Live ruleset, base driver: the live ruleset today (it has `gate`) disagrees
  with 97ac438d6's recorded shape. 7 rows fail, the six exit-code rows among
  them with a bare `rc=1`. That is the instance's symptom, which the shape
  reproduces.
- Live ruleset, this branch's driver: the same 7 rows fail, and each now
  names its cause. The four `policy_lint` rows read
  `37 ERROR line(s), first: ERROR [required-contexts] ... has \`gate\``. The
  three mutants rows read `MUTANTS: the entry point exited 1 ...`.
- `--no-live`, which puts a failing `gh` first on PATH, at both ends: the
  no-remote rows hold. The only row that fails is
  `pr / nothing skipped in a full clone`, which is required to fail when the
  API is unreachable. With the live input withdrawn, the no-remote shape
  holds. **No shape-borne defect exists.**

**The fix** is in `tools/policy/policy_lint_envmatrix.mjs`, the one module
(this is a departure from the roster's file list; see the end of this
section):
1. `rcRow(name, ok, r, extra)`: every row keyed on a subprocess's exit code
   appends `why(r.out)`. That is six rows that printed only `rc=`, plus
   shallow's, which already appended it by hand.
2. `why()` ranks the program's own verdict first: a `FIXTURE VACUOUS/OVER-FIRES`
   line, or a `MUTANTS:` line other than the NOT-measured line a no-remote
   clone prints by design. Next come the ERROR findings, counted with the
   first one quoted, and only then `fatal:`, `skip` and exception lines. The
   old order fell through to the last three `fatal:`/`skip` lines. A clone
   with no origin/main prints benign
   `fatal: ambiguous argument 'origin/main'` lines, so the mutants refusal
   was hidden behind them.
3. A self-check runs before any shape is built. It feeds two recorded failure
   outputs (cut from the reproduced no-remote arm) through `rcRow`, and
   refuses with `MATRIX MUTE` if either detail fails to name the program's
   verdict. It runs in this PR's own env-matrix job, because the workflow
   checks this driver out from HEAD ("owned, not pinned").

The roster lists `.github/workflows/governance.yml`. The job definition
needed no change: the defect is in what the driver prints, and the driver is
the file the job runs from the PR head.

**Alternatives.** (a) Read the live ruleset once per matrix run and hand it to
every arm. Arms would then agree within a job. But that means injecting live
state into `policy_lint`'s production path, from a driver that exists to run
that path unmodified, and it would not have told anyone why the arm was red.
(b) Retry an arm on `rc=1`. That turns a real ruleset change into a pass, so
the matrix would hide the class it exists to catch. (c) Treat the red as a
flake and re-run. That was the carry's reading, and it is what a bare
`rc=1` invites. The fix taken makes the cause visible and changes no row's
verdict.
